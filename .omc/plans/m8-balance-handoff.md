## 3. 확정된 메커니즘 사실 (전부 코드로 확인, 파일:라인 포함)

### 3.1 `applyShipTypeBase` — `src/items/loadout.ts:216-225`

```
damage    *= (10000 + bp) / 10000
fireRate  *= 10000 / (10000 + bp)      // 양수 bp = 쿨다운 ↓ = 연사 ↑
maxHp     += round(100 * bp / 10000)   // BASE_HP_REF = 100 (loadout.ts:46)
move      *= (10000 + bp) / 10000
```

- `bp === 0` 이면 해당 축은 **무연산**. striker 는 4축 전부 0 이라 이 함수가 완전한 no-op 이다.
- 정규화 범위: `[-9000, 20000]` (`normalizeShipBaseBp`).

### 3.2 fireRate bp 의 죽은 구간 **[실측 · 산술 검산]**

기본 `fireCooldown 6` 에 `round(6 * mult)` 를 걸기 때문에 **`-770 ≤ bp ≤ 909` 구간 전체가 파생 스탯에 아무 흔적을 남기지 않는다** — 폭 **1680bp**. 즉 이 구간의 튜닝은 전부 무의미하다.

P0 기준 경계 검산:

| 결과 cd | 조건 |
|---|---|
| 4 | bp ≥ 3334 |
| 5 | bp ≥ 910 |
| 6 | -770 ≤ bp ≤ 909 (죽은 구간) |
| 7 | bp ≤ -770 |
| 8 | bp ≤ -2000 |

P1 이후는 스킬트리 `fireRatePct` 가 곱해져 기체마다 경계가 달라진다. **fireRateBp 를 만질 땐 반드시 해당 프로파일에서 파생 `fireCd` 가 실제로 바뀌는지 먼저 확인하라.**

### 3.3 `maxHpPct` 는 비율이 아니다 — `src/items/loadout.ts:142`

```
lo.maxHpAdd += sums.maxHpFlat + Math.round((BASE_HP_REF * sums.maxHpPct) / 100)
```

`BASE_HP_REF = 100` 은 **고정 상수**다. 즉 `maxHpPct`·`maxHpBp` 는 현재 HP 에 비례하지 않고 **항상 100 기준 flat 가산**이다. `1000bp = 정확히 +10 HP`, P0·P1 동일.

> ⚠️ **"후반에 더 커지는 비율"이라는 전제로 튜닝하면 의도와 정반대가 된다.**
> 결과적으로 **`maxHpBp` 는 사실상 P0 전용 레버**다 — P0 기준 HP 100 대비 +N 은 크지만, P1 기준 HP 128~172 대비 같은 +N 은 상대적으로 훨씬 작다.

### 3.4 `pierce` / `bulletCount` 는 시너지 곱 후 `Math.floor`

`src/items/skills.ts`. 0.25 / 0.5 단위 노드는 시너지 배율 크기에 따라 계단이 어긋난다 — 같은 노드 1점이 어떤 빌드에선 +1, 어떤 빌드에선 +0 이다. 정수 경계를 넘기는 조합인지 확인 없이 소수 노드를 조정하지 마라.

### 3.5 캡스톤은 7종이 사실상 동일하다 — `src/items/loadout.ts:233-237`

```
offense → CAP_FIREPOWER_LASER   (탄막 소거 레이저)
defense → CAP_SURVIVAL_CRIT     (치명 1회 무효)
utility → CAP_MOBILITY_DASH     (대시 잔상 소거)
```

캡스톤 효과는 **affinity 로만** 결정되므로 7종 캡스톤이 이름만 다르고 효과가 전부 같다. 기체 정체성 차별화를 캡스톤에 기대할 수 없다 — 전면 재작업에서 다뤄야 할 구조적 항목이다.
