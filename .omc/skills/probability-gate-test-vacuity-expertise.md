# 확률 게이트 도입은 기존 테스트를 조용히 공허하게 만든다

## The Insight

**"조건부 확률을 레코드마다 굴리기" → "게이트를 단위마다 한 번 굴리기"로 바꾸면, 그 축의
기존 테스트 중 고정 픽스처를 쓰는 것 전부가 `[]` 와 `[]` 를 비교하는 항진이 된다.**

원리는 이렇다. 구 모델에서는 레코드를 N개 밀어 넣으면 `1-(1-p)^N` 로 거의 확실히 히트가 났다 —
그래서 "레코드 300개짜리 픽스처" 가 유효한 표본이었다. 게이트는 **레코드 수와 무관하게 단위당
한 번만** 굴리므로, 같은 픽스처의 기대 히트가 `N·p` 에서 **`p` 로 떨어진다**(3% 면 97% 가 빈 결과).

그리고 빈 결과끼리의 비교는 **언제나 통과한다.** 결정론 단언(`f(x)).toEqual(f(x)`), 등식 단언
(`정산 결과).toEqual(순수 파생`), 불변 단언 — 전부 초록인 채로 **아무것도 증명하지 않게 된다.**
호출을 통째로 지워도 통과한다.

## Why This Matters

이것이 **조용하다**는 게 핵심이다. 게이트를 넣은 커밋에서 스위트는 전량 초록이고, 리뷰가
fold 해시를 직접 계산해 보기 전까지 아무 신호가 없다. 실측 예:

- `lootSweep(1, 40)` 시드 집합의 게이트 잔여 = **9531** (> 300 이라 MISS)
  → "정산 결과 = 순수 파생" 이라는 그 파일의 **유일한 등식 단언**이 `[]` vs `[]` 가 됐다.
  `settleRun` 이 `blueprintDropsFromLoot` 호출을 잃어버려도, `victory` 를 안 넘겨도 통과.
- 고정 시드 `[11, 22, 33]` 잔여 = **1836** → 결정론 단언 공허.

같은 커밋이 만든 **역방향** 함정도 있다. "안 나온다" 를 단일 런으로 재면, 게이트를 지우는
뮤테이션이 **통과한다** — 그 한 런이 3% 를 못 뚫으면 결과가 0 이라서다. 실제로 밟았다.

## Recognition Pattern

- 확률/게이트 상수를 새로 세우거나 "레코드별 → 단위별"로 판정 구조를 바꿨다.
- 그 축의 테스트에 `for (let seed = 1; seed <= 300; ...)` 처럼 **한 호출에 레코드를 쌓는**
  픽스처가 있다.
- `expect(a).toEqual(b)` 인데 `a` 가 비지 않았음을 **아무도 단언하지 않는다.**
- 확률을 낮췄는데 스위트가 **전량 초록**이다 ← 가장 위험한 신호.

## The Approach

### 1. 표본을 늘릴 축을 다시 정한다 — 레코드가 아니라 **단위(런)** 다

게이트가 단위당 한 번이면 표본도 단위로 세야 한다. 레코드를 늘리는 것은 분포만 바꾸고
기대 건수를 안 움직인다. 헬퍼를 하나 만들어 그 축의 전 테스트가 같은 형태를 쓰게 한다.

### 2. "비지 않음"을 등식 옆에 명시로 못 박는다

등식만 있으면 공허해질 수 있다. **히트가 나는 단위를 찾아서** 그것으로 등식을 재고, 못 찾으면
던진다. 이 형태는 게이트가 죽어도(확률 0) 빨개진다.

### 3. "안 나온다" 는 **같은 단위 집합을 두 조건으로** 돌려 대조한다

`expect(f(x, false)).toEqual([])` 단독은 무의미하다. 같은 집합을 `true` 로 돌려 `> 0` 을 함께
단언해야 "0 인 이유가 게이트"임이 성립한다. 짝이 없으면 축이 죽은 것과 구분되지 않는다.

### 4. **뮤테이션으로 검증한다** — 이 축은 특히 필수다

게이트 삭제 · 확률 0 · 상수 드리프트를 각각 넣어 **해당 단언이 정확히 하나 빨개지는지** 본다.
공허한 단언은 뮤테이션에서 조용하므로, 이것이 공허를 찾는 유일하게 확실한 방법이다.

### 5. `Function.length` 로 arity 를 잠그지 마라

**기본값 앞까지만 센다.** `(loot, victory = false)` 는 1 이고, 인자를 기본값으로 되살려도 그대로
1 이다. 시그니처를 잠그려면 **선언 텍스트**를 읽어라.

## Example

공허해진 형태와 고친 형태의 대비 — 코드가 아니라 **축의 이동**을 보라.

```ts
// ❌ 게이트 도입 후: 97% 확률로 [] vs [] (레코드 축으로 표본을 만들었다)
const loot = Array.from({ length: 300 }, (_, i) => rec(i));
expect(f(loot)).toEqual(f(loot));

// ✅ 런 축으로 표본을 만들고, 비지 않음을 못 박는다
let hitRun = -1;
for (let run = 0; run < 2000 && hitRun < 0; run++) {
  if (f(mk(run)).length > 0) hitRun = run;
}
expect(hitRun, '2000런 안에 히트가 없다 — 게이트가 죽었거나 확률이 오타다')
  .toBeGreaterThanOrEqual(0);
const a = f(mk(hitRun));
expect(a.length).toBeGreaterThan(0);   // 공허 재발 방지
expect(f(mk(hitRun))).toEqual(a);
```

## 함께 오는 것 — 대체된 옛 보정을 찾아라

게이트가 "총량"을 상수 하나로 끌어내면, **그 총량을 지키려 존재했던 보정이 잔재가 된다.**
이 리포에서는 ADR-0038 의 인기 배율 역수 보정이 그랬다 — 게이트가 획득률과 건수를 구조적으로
분리하자 보정은 기대치가 아니라 **추첨 비중만 근거 없이 틀어놓는** 것이 됐다.

⚠️ 그 인자를 `void` 로 남기지 마라. 남기면 그 축의 불변 테스트가 **전부 항진**(어떤 값을 줘도
같은 결과)이 된다. 인자를 제거하면 불변이 통계적 근사에서 **시그니처가 보장하는 항등**이 되고,
테스트는 선언 텍스트를 재는 형태로 바뀐다.
