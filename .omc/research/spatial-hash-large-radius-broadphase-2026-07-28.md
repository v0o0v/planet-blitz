# 공간 해시 broad-phase — 큰 반경 엔티티가 판정에서 통째로 빠져 있던 결함

- 날짜: 2026-07-28
- 브랜치: `fix/spatial-hash-large-radius-broadphase`
- 발단: `.omc/research/invasion-gravwell-slow-axis-2026-07-27.md` §2-1 의 부수 발견 —
  `gravwell` 의 `hazardRadius` 를 760 과 1,520 으로 두고 96시드 9레벨 스윕을 돌렸는데
  **9행 전부 바이트 동일**이었다(반경 약 650 위로 기여가 정확히 0).

## 1. 원인 — 추정은 맞았고, 범위는 추정보다 넓었다

### 1-1. 코드로 확정한 사실

`src/sim/collision.ts` 의 `SpatialHash` 두 함수가 **비대칭**이다.

| | 코드 | 귀결 |
|---|---|---|
| 등록 | `insert` 가 `floor(entity.x / cellSize)` **한 칸**에만 push | 엔티티의 반경은 등록에 **전혀 반영되지 않는다** |
| 질의 | `query(x, y, radius)` 가 `radius` 로만 셀 범위를 넓힘 | 훑는 범위에 **표적 반경이 빠져 있다** |

- 셀 크기: `GRID_CELL_SIZE = 256` (`src/sim/world.ts:302`)
- 등록 지점: `resolveCollisions` (`src/sim/world.ts:3057`), 19개 `kind` 화이트리스트
- 질의 지점 2곳: 아군탄(`world.ts:3122`) · 플레이어 접촉/픽업(`world.ts:3337`)

접촉의 참 조건은 `|중심거리| <= 탐침반경 + 엔티티반경` 인데, 훑는 범위는 `탐침반경` 뿐이다.
**엔티티 반경만큼의 띠가 broad-phase 에서 통째로 사라진다.** 엔티티 중심이 탐침의 셀 밖으로
나가는 순간, 반경이 아무리 커도 후보 목록에 들어오지도 않는다 — 정확도 문제가 아니라
**후보 누락**이라 아래 정밀 판정(`sweptCircleHitT` 등)은 손쓸 기회조차 없다.

`hazardRadius` 의 실효 상한이 약 650 인 것도 여기서 나온다. 플레이어 질의는 `pickR =
player.radius`(≈28)로 훑으므로 셀 범위가 1~2칸이고, 그 밖의 셀에 중심이 있는 장판은
반경과 무관하게 후보에서 빠진다.

### 1-2. 이미 두 곳이 이 사실을 알고 있었다 (그런데 전역 수정은 안 됐다)

- `src/sim/invasion/wallIndex.ts:10-14` — "SpatialHash 는 엔티티를 중심 셀 1칸에만 넣는다"
  라고 명시하고, 길이 12,000u 짜리 벽을 위해 **자체 인덱스를 따로 만들었다**.
  즉 벽은 이 결함을 우회했지만 나머지 엔티티는 방치됐다.
- `src/sim/invasion/facility.ts:812` — 반경 강화축이 죽어 있다는 실측을 남기되,
  "전역 broad-phase 를 고치면 모든 해저드가 한꺼번에 바뀐다"는 이유로 레인 범위 밖으로 뺐다.

## 2. 파급 범위 — **해저드 전용 결함이 아니다** (이게 본체다)

발단이 해저드였기 때문에 "큰 장판만의 문제"로 보이지만, 실측하면 **반경을 가진 모든 엔티티가
셀 경계에서 확률적으로 판정을 흘리고 있었다**.

### 2-1. 카탈로그 반경 실측 (침공 4기지 × 6,000틱)

격자 등록 대상의 반경 최댓값:

| kind | 실측 최대 반경 |
|---|---|
| `hazard` | 300 |
| `enemy` | 54 (카탈로그 최대 140) |
| `facilitySpawner` | 38 |
| `facilityGun` | 36 |
| `facilityHazard` | 30 |
| `gem` | 20 |
| `enemyBullet` | 8 |

카탈로그 전체로는 적 최대 140 · 보스 최대 130 · 설비 최대 38 · 해저드 기본값 최대 520
(`data/invasion/facilities.ts`) 이다.

### 2-2. 반경 54 짜리 잡몹도 빠졌다

플레이어 피격 판정점은 `PLAYER_HIT_RADIUS = 8` 이고 브로드페이즈 탐침은 `player.radius`(28)다.
잡몹 반경 54 면 접촉 거리는 62 인데, 질의가 넓히는 폭은 28 뿐이다. 셀 경계(256)를 사이에 두면
**접촉 거리 안에 있는 잡몹이 후보에서 빠진다** — `tests/collision.test.ts` 의
"셀 경계 너머의 보통 잡몹도 접촉 거리 안이면 잡힌다" 케이스가 이 상황을 최소 재현한다
(수정 전 코드에서 실패).

아군탄 질의도 같다. 탄은 선분 전체를 덮는 원(`중점 + 반길이 + 탄 반경`)으로 훑는데 **표적 반경이
빠져 있어**, 셀 경계 너머에 있는 적은 선분이 실제로 관통해도 후보로 올라오지 않았다.

### 2-3. 세 갈래 중 어느 쪽이 난이도를 움직였나 — 분리 실측

수정을 두 갈래로 나눠 각각의 기여를 쟀다(24시드 침공 밴드).

- **변이 B** = 임계(160) 이하 엔티티의 경계 누락만 수정. 큰 해저드는 **예전 그대로 방치**.
- **변이 C** = 전체 수정(변이 B + 초대형 선형 목록).

| | 하위 (목표 ≥85) | 중하 (목표 55~80) | 중위 (목표 25~55) |
|---|---|---|---|
| 수정 전 | 100.00 | 71.43 | 31.94 |
| 변이 B | 통과 | 통과(55~80) | **21.53** |
| 변이 C (전체) | 통과 | **52.38** | **17.36** |

**중위 기준 −14.58pp 중 −10.41pp 가 변이 B**, 즉 "보통 엔티티가 셀 경계에서 빠지던" 몫이다.
큰 해저드가 살아난 몫은 −4.17pp 로 **소수**다. 발단은 해저드였지만 **결함의 무게중심은
일반 전투 판정에 있었다.**

이 사실은 실무적으로도 결정적이다 — sim 쪽 해저드 상한(`UTILITY_HAZARD_RADIUS_CAP_CP` 등)을
아무리 조여도 밴드를 되돌릴 수 없다(해저드 기여를 전부 없앤 변이 B 에서도 중위 21.53 < 25).

## 3. 수정 — 2단 구조 (셀 확장 + 초대형 선형 목록)

`src/sim/collision.ts`:

1. **셀 확장** — `query` 가 `radius + maxHashedRadius` 로 셀 범위를 넓힌다.
   `maxHashedRadius` 는 그 틱에 **실제로 등록된** 반경의 최댓값이다.
2. **초대형 선형 목록** — 반경이 `OVERSIZED_RADIUS_THRESHOLD = 160` 을 넘는 엔티티는 셀에
   넣지 않고 별도 배열에 모아, 질의마다 원-원 판정으로 거른다.

### 왜 이 형태인가

- **확장폭을 상수로 두면 질의가 폭발한다.** 반경 1,520 짜리 장판 하나 때문에 모든 질의가
  13×13 셀을 훑게 된다. 실제 등록 최댓값을 쓰면 침공 54 · PvE 140 수준이라 대개 셀 경계
  근처에서만 한 칸 늘어난다.
- **임계 160 의 근거는 카탈로그 실측이다**(§2-1). 전투 엔티티(적 140 · 보스 130 · 설비 38)는
  전부 임계 아래로 들어가고, 임계를 넘는 것은 사실상 해저드 장판뿐이다. 실측상 반경 > 256 인
  엔티티는 **틱당 최대 1개 · 평균 0.04개** 라 선형 목록은 거의 비어 있다.
- **다중 셀 등록은 쓰지 않았다.** 큰 엔티티를 여러 셀에 넣으면 한 질의가 같은 엔티티를 **두 번**
  콜백하고, 아군탄 피해 해소가 그 중복을 그대로 두 번 적용한다(중복 제거에는 질의별 방문
  표식이 필요해 해시 필드나 사이드 맵이 늘어난다).
- **broad-phase 계약은 유지된다.** 초대형 목록의 원-원 판정 `|중심거리| <= 탐침반경 +
  엔티티반경` 은 어떤 형태의 겹침에도 **필요조건**이라 후보를 놓치지 않는다.

### 결정론 (ADR-0005)

- RNG·wall-clock 미소비. 추가된 연산은 f64 기본 사칙연산·비교뿐이다.
- 순회 순서: 셀을 고정 `(cy, cx)` 순으로 훑고 → **그다음** 초대형 목록을 삽입 순서로 훑는다.
  삽입은 엔티티 배열 순서라 시드 무관하게 고정이다.
- 판정 **순서가 바뀌므로** 골든은 정당하게 움직인다(§5).

### 회귀 테스트 (`tests/collision.test.ts`, 3건 추가)

세 건 모두 **수정 전 코드에서 실패**함을 확인했다(비공회전 검증):

1. 엔티티 반경이 셀보다 커도 후보로 들어온다 (장판 반경 900 · 탐침 거리 700)
2. 반경을 더 키우면 그만큼 더 멀리서 잡힌다 (760 vs 1,520 — 발단 증상의 직접 반증)
3. 셀 경계 너머의 보통 잡몹도 접촉 거리 안이면 잡힌다 (§2-2)

## 4. 밸런스 재조정

§2-3 이 보인 대로 밴드가 **목표 아래로** 내려갔다(중하 52.38 < 55 · 중위 17.36 < 25).
추가로 `tests/invasionE2E.test.ts` 의 "L1→L2→L3 완주 후 코어 파괴" 가 실패했다 —
참조봇이 만석 배치를 더는 클리어하지 못한다.

**판단: 재기준화가 아니라 밸런스 재조정이 필요하다.** 근거는 두 가지다.

- 밴드가 **설계 목표 범위 밖으로** 나갔다. 상한을 여는 과거 3세대와 성격이 다르다
  (그때는 목표 안에서 분포가 이동한 것이었다).
- e2e 의 만석 배치가 **클리어 불가**가 됐다. 이건 분포 이동이 아니라 진행 가능성의 문제다.

### 4-1. 레버 선정 — 기물만이 두 밴드를 각각 조준한다

24시드 스윕. 먼저 기물 이외의 축부터 봤다.

| 후보 | 중하 (55~80) | 중위 (25~55) |
|---|---|---|
| 변경 없음 | 52.38 ✗ | 17.36 ✗ |
| 레벨 기울기 3/2 → 5/4 | 57.14 | 18.75 |
| 레벨 기울기 3/2 → 1 | 62.50 | 21.53 |
| 승급 임계 완화 | 64.88 | 22.22 |
| 기물 중하 5 → 3 | 86.31 ✗ | **17.36 (불변)** |

두 가지가 드러났다.

- **레벨·승급으로는 중위가 목표(25)에 닿지 못한다.** 최대가 22.22 다.
- **기물은 중하를 52 → 86 으로 미는데 중위는 한 자리도 안 움직인다.** 선행 램프가 기물을
  `nn<=14` 에만 걸어 뒀기 때문이다(중하·중위 모두 5 였고, 위 후보는 중하만 내렸다).
  즉 **기물이 유일한 분리 레버**라는 선행 레인의 발견이 그대로 재확인됐고, 중위를 조준하려면
  중위 구간의 기물 수를 직접 내려야 했다.

### 4-2. 채택 — `props` 램프 한 줄

```
props  이전: nn<=4 ? 0 : nn<=7 ? 2 : 5
       이후: nn<=4 ? 0 : nn<=7 ? 2 : nn<=14 ? 4 : 3
```

기물 수를 중하/중위로 나눠 스윕한 결과:

| `중하/중위` | 중하 (55~80) | 중위 (25~55) |
|---|---|---|
| 5/5 (변경 없음) | 52.38 ✗ | 17.36 ✗ |
| 4/4 | 70.83 ✓ | 27.78 ✓ (여유 2.8pp) |
| **4/3 (채택)** | **70.83 ✓** | **40.28 ✓** |
| 4/3 + 승급 완화 | 79.76 ✓ (천장 아슬) | 45.83 ✓ |
| 3/3 | 86.31 ✗ | 40.28 ✓ |

채택안은 **램프 한 줄만** 옮기면서 두 밴드를 목표 **중앙**에 놓는다.

| 하위 | 100.00 | 100.00 | 100.00 | 85+ ✓ |

대응이 "상한 열기"가 아니라 램프 재조정이었다.

### 4-4. 왜 중위(3)가 중하(4)보다 적은가 — 역전이 아니다

- 중위는 **등급 3 · 승급 3** 이라 기물 1기당 강도가 중하보다 훨씬 세다. 줄어든 것은 개수뿐이고
  총 위협은 여전히 중위가 위다 — 실측 클리어율 40.28% < 70.83% 가 그 증거다.
- 중위는 `propShift = 3`(nn>=18)이라 **다른 종류**가 선다. 개수를 그대로 두면 상위 기물이
  여섯 소켓을 채워 회피 공간이 사라진다.
- 나머지 전 축(레벨 · 굴곡 템플릿 · 편대 만석 · 설비 만석 · 최난도 보스)이 중위에서 최대다.

    명시했다 — 인용된 수치와 위반 경계값은 선행 세대 것이다.

### 4-6. 성능 — 회귀 없음

broad-phase 는 핫 패스라 따로 쟀다(`src/bench/simBench.ts`).

**① 고정 합성 부하(2,300 적탄 + 200 적 · 스크롤 맵) — 이쪽이 깨끗한 A/B 다.**
부하가 주입식이라 판정이 바뀌어도 개체 수가 유지된다(실측 양쪽 모두 `sustained 2158
projectiles · 13 active walls` 로 동일).

| `GRID_CELL_SIZE` | 수정 전 | 수정 후 |
|---|---|---|
| 256 (현행) | 0.539 ms/tick | **0.562 ms/tick** (+4.3%) |

60fps 예산 16.67 ms 대비 **29.7배 여유**. 질의 폭이 조금 넓어진 만큼의 실제 비용이 보이고,
그 크기가 4% 대다.

**② 침공 3레이어 서버 재실행 예산(18,000틱)**: 수정 후 0.59~0.86s / 예산 20s (EF
`SOFT_RERUN_BUDGET_MS`). ⚠️ **이 지표는 A/B 로 쓸 수 없다** — 같은 코드에서 반복 측정만으로도
0.59 ↔ 0.86s 로 흔들리고(런 궤적이 판정에 따라 달라진다), 수정 전 값 0.74~0.77s 는 그 폭 안에
있다. 여기서 말할 수 있는 것은 **예산 대비 20배 이상 여유** 까지다.

비용이 작은 이유는 §3 의 두 설계 선택이다. 셀 확장폭이 **실제 등록 최댓값**(침공 54 ·
PvE 140)이라 셀 한 칸을 넘지 않고, 선형 목록은 **틱당 평균 0.04개**로 사실상 비어 있다.
확장폭을 상수 256 으로 뒀다면 점 질의가 항상 3×3 셀을 훑어 비용이 이보다 훨씬 컸을 것이다.

### ⚠️ invasion 골든이 움직인 것 자체가 물증이다

선행 3개 세대(탄 대 벽 · 다중 명중 해소 순서 · 런 풀 커브)에서는 invasion 배열이 **바이트
동일**이라, "골든이 그 구간을 안 밟는다"는 단서를 매번 따로 붙여야 했다. 이번에는

에서만 나는 것이 아니라 **모든 틱의 모든 접촉 판정**에 걸려 있었다는 직접 증거다.

### 실행 방법 — 이 리포에는 `vite-node` 가 없다

두 녹화 스크립트의 문서화된 실행법은 `npx vite-node scripts/record*.ts` 인데
`node_modules/.bin` 에 `vite-node`(및 `tsx`·`ts-node`)가 **없다**. 두 스크립트 모두 환경 변수가
켜져 있으면 **모듈 로드 시점에** 기록하므로, 임시 vitest 파일에서 `import` 만 시켜 우회했다.

```ts
env['RECORD_STRIKER_BASELINE'] = '1';
env['RECORD_ENCOUNTER_BASELINE'] = '1';
await import('../scripts/recordStrikerBaseline.js');
await import('../scripts/recordEncounterBaseline.js');
```

`scripts/deno-verify/fixtures.json` 만 `REGEN_DENO_FIXTURES=1 npx vitest run
tests/denoFixture.test.ts` 로 정상 경로 재생성이 된다.

## 6. 서버 재배포

`src/sim/collision.ts` 가 바뀌었으므로 `verify-invasion` Edge Function **재배포는 필수**다.
절차 정본은 `.omc/skills/planet-blitz-supabase-deploy-workflow.md`.

⚠️ 이 리포가 반복적으로 확인한 함정 — **골든/픽스처 그린은 재배포 불필요의 근거가 못 된다.**
서버는 번들에 들어간 sim 으로 침공 리플레이를 재계산하므로, `src/sim` 이 바뀐 채 EF 를 방치하면
**모든 침공이 해시 불일치로 거부**된다.
(이번에는 골든 자신이 재배포 필요를 보고했다 — §5 의 invasion 3/3.)

### 6-1. ✅ `verify-invasion` EF 재배포 완료

| 항목 | 값 |
|---|---|
| 번들 소스 커밋 | `c3f61af` (= `origin/main`, **대조 확인함**) |
| 번들 | 96 모듈 · 214.93KB (2026-07-26 기준 210KB 에서 증가 = sim 변경 실증) |
| 버전 | **v35 → v36** · ACTIVE |
| 업로드 자산 | `deno.json` + `index.ts` **둘뿐** (자립 번들 치환이 제대로 됐다는 방증) |

부팅 스모크(anon 키로 게이트 통과):

```
POST /functions/v1/verify-invasion  body {}
→ 400 {"status":"rejected","reason":"malformed-invasion-id","attackerWon":false,...}
```

그리고 그 `reason` 문자열이 **배포한 번들에 정확히 1회** 존재하고 게이트웨이 문자열
(`UNAUTHORIZED_NO_AUTH_HEADER`)은 **0회** 임을 대조했다 — 게이트웨이가 아니라 우리 코드가
실행됐다는 확증은 이 대조까지 해야 성립한다.

**함정 하나 추가** — `spb functions deploy` 는 entrypoint 를 **프로젝트 루트 기준**으로 찾는다.
절차 문서대로 `supabase/functions/verify-invasion` 에서 실행하면
`Entrypoint path does not exist - .../verify-invasion/supabase/functions/verify-invasion/index.ts`
로 **400** 이 난다. 번들·치환은 그 디렉터리에서 하되 **배포는 워크트리 루트에서** 해야 한다.

### 6-2. ✅ 마이그레이션 원격 적용 완료

`scripts/apply-invasion-props-rebalance-migration.ps1` 로 적용했다.

```
powershell -ExecutionPolicy Bypass -File scripts\apply-invasion-props-rebalance-migration.ps1
```

선행 스크립트와 같은 규율을 따른다 — 오배포 가드(프로젝트 이름에 `planet` 포함 확인) ·
NPC 20행 존재 확인 · `[IO.File]::ReadAllText(..., UTF8)` 로 읽고 **UTF-8 바이트로 전송**
(문자열로 보내면 한글 주석이 깨져 400 파싱 오류가 난다) · `schema_migrations` 기록 ·
적용 후 20행 전수 검증(boss / props / rarity / ascension). 콘솔 출력은 **ASCII 전용**이다.

적용 결과 — `[OK] all 20 rows match the expected ramp`. `props` 열이 새 램프 그대로다:

| nn | 1~4 | 5~7 | 8~14 | 15~20 |
|---|---|---|---|---|
| props | 0 | 2 | **4** | **3** |
| boss | none | 2 | 2 → 0 | 0 → 1 |
| rarity | 0 | 1 | 1 → 3 | 3 |
| ascension | 0 | 0 | 1 → 2 | 2 → 3 |

**이로써 클라 sim · EF(v36) · 원격 시드 배치가 모두 같은 세대로 정렬됐다.** 잔여 없음.
