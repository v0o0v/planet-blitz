## 2. 카탈로그 대조표 — 무엇이 잘려 있었나

세 `kinds` 상한이 각각 무엇을 자르는지 카탈로그 실제 길이와 대조했다. 상한의 20기지 최댓값은
`max(nn=1..20)` 이다.

| 카탈로그 | 길이 | 램프 상한 식(변경 전) | 20기지 최대 노출 | 잘린 구간 |
|---|---|---|---|---|
| `FORMATIONS` | 12 | `min(8, 1 + (nn+1)/3)` | 8 | **8..11** — `toxar-corrosion` · `toxar-blight` · `kras-breaker` · `kras-piercer` |
| `INVASION_FACILITIES` | 17 | `min(9, 2 + (nn*2)/5)` | 9 | **9..16** — `venomvent` · `blightpool` · `corrosivemist` · `toxinturret` · `heavyrail` · `siegecannon` · `breachturret` · `demolisher` |
| `L3_PROPS` | 6 | `min(6, 1 + nn/4)` | 6 | 없음 |
| `DEFENSE_BOSSES` | 3 | `boss` CASE 가 0·1·2 전부 사용 | 3 | 없음 |

→ **잘린 것은 두 축뿐**이고, 정확히 Lane9 신규 방어체 12종이다. 기물·보스는 이미 전량 노출이라
이 레인이 손댈 것이 없었다(브리핑이 `propKinds` 도 의심 대상으로 지목했지만 실제로는 상한
6 = 카탈로그 길이 6 이라 구멍이 없다).

부수 확인: `facilityShift` 라는 축은 **존재하지 않았다**. 설비는 `catalogId = i % facilityKinds`
로만 배정돼 창을 밀 수단 자체가 없었고, 그래서 상한을 올리는 것 말고는 뒷부분에 닿을 방법이
없었다 — 그 상한 인상이 곧 난이도 변경이라 계속 미뤄져 온 구조다.

## 3. 노출 설계 판단 — "여유가 있는 밴드에만, 문수가 아니라 창으로"

### 3.1 어느 밴드에 열 것인가 → 하위(nn 1..7) 단독

| 밴드 | 현재(6세대) | 목표 | 여유 | 판단 |
|---|---|---|---|---|
| 하위 #01~#07 | 100.00% | 85+ | **15.0pp**(아래로만) | ✅ 여기에 연다 |
| 중하 #08~#14 | 70.83% | 55~80 | 15.8pp / 9.2pp | ❌ 안 건드린다 |
| 중위 #15~#20 | 40.28% | 25~55 | 15.3pp / 14.7pp | ❌ 안 건드린다 — 최저 기지 `#16` 이 여기 있다 |

중위를 건드리면 `#16` 의 "클리어 불가 기지 없음" 불변식이 먼저 깨진다. 복원 레인이 실제로 그렇게
깼다(당시 4.2 → 0%). `#16` 계단 레인(PR#173)이 그 여유를 넓히려 시도했지만 **원인이 램프 값이
아니라 L3 `affixSeed` 추첨**이라 수치를 바꾸지 않고 끝났다.

6세대(broad-phase 수정 + 기물 재조정)에서 `#16` 은 4.2 → **20.8%(5/24)** 로 올라가 여유가 늘었다.
그래도 이 레인의 판단은 바뀌지 않는다 — **여유가 있다는 것과 그 여유를 가시성에 쓰는 것이
좋은 거래라는 것은 다른 명제**이고, 하위에 열어도 목적이 온전히 달성되기 때문이다.
중위 여유는 다음 밸런스 레인이 쓸 몫으로 남긴다.

### 3.2 종류를 늘릴 것인가 문수를 늘릴 것인가 → **창(shift)만 민다**

기지당 설비 문수·웨이브 수·레벨·등급·승급·기물·보스를 **한 줄도 바꾸지 않았다**. 바꾼 것은
"어느 종류가 서느냐" 하나뿐이다. 그래서 난이도 변화의 원천이 **종류 간 실효 화력 차이**로
한정되고, 그 차이가 작다는 것이 복원 레인의 실측이다(신규 8종 노출 시 중위 74.31 → 75.69).

구현은 하위 밴드에서만 창 크기를 **전 카탈로그**로 열고(`formationKinds=12` · `facilityKinds=17`)
시작점을 shift 로 민다. shift 값은 **누적합** — 기지 `nn` 의 시작점 = `nn` 미만 기지들이 소비한
슬롯 수. 그래서 창이 이어붙어 카탈로그를 빈틈없이 한 바퀴 덮는다.

- 하위 설비 슬롯 합 = 2+2+3+3+4+4+5 = **22 ≥ 17** → 17종 전부 + 5슬롯 겹침
- 하위 웨이브 슬롯 합 = 1+1+1+2+2+2+3 = **12 = 12** → 낭비 0 의 완전 타일링

| nn | 설비 catalogId (전 → 후) | 편대 catalogId (전 → 후) |
|---|---|---|
| 1 | 0,1 → **0,1** | 0 → **0** |
| 2 | 0,1 → **2,3** | 0 → **1** |
| 3 | 0,1,2 → **4,5,6** | 0 → **2** |
| 4 | 0,1,2 → **7,8,9** | 0,1 → **3,4** |
| 5 | 0,1,2,3 → **10,11,12,13** | 0,1 → **5,6** |
| 6 | 0,1,2,3 → **14,15,16,0** | 0,1 → **7,8** |
| 7 | 0,1,2,3,0 → **1,2,3,4,5** | 0,1,2 → **9,10,11** |
| 합집합 | 0..8 → **0..16** | 0..7 → **0..11** |

중하·중위가 여전히 설비 0..8 · 편대 0..7 을 덮으므로 **20기지 전체 합집합 = 두 카탈로그 전량**.

부수 효과로 `#07` 의 중복 배치(소켓 4개가 `0,1,2,3` 다음 다시 `0`)가 사라져 5문이 전부 다른
종류가 됐다 — 종전 램프에서 `facilities`(5) > `facilityKinds`(4) 였던 구간이다.

### 3.3 왜 하위가 "노출 자리"로 최선인가

하위 7기지는 진행상 **필수 5회 구간**이라 모든 플레이어가 반드시 지나간다. Lane9 방어체를
"처음 보는 자리"로는 여기가 가장 도달률이 높다. 서사적으로는 톡사르·크라스 특산 설계도가
하위 기지에 서는 것이 어색할 수 있으나, 이 레인의 목적은 난이도 서열이 아니라 **가시성**이고
난이도 서열은 레벨·등급·승급·보스가 이미 담당한다(그 축들은 전부 불변).

## 4. 난이도 중립 — 구조 + 실측 두 겹

### 4.1 구조: nn>=8 이 바이트 동일

램프 식을 `nn <= 7` 분기 안에서만 바꿨다. 따라서 중하·중위 20기지 중 13기지의 배치 JSON 이
**입력 수준에서 동일**하다. 승률이 같은 이유가 "다시 쟀더니 같더라"(측정 오차가 낄 자리가 있는
진술)가 아니라 **"입력이 같아서 같다"** 가 된다. `#16` 의 5/24 도 정의상 보존된다.

이 성질을 계약으로 굳히려고 회귀 테스트를 추가했다 —
`중하·중위(nn 8..20) 배치가 Lane9 노출 확장 전과 바이트 동일하다`. 확장 **전** 식을 테스트 안에
그대로 박아 두고 `nn>=8` 의 `catalogId` 를 대조하므로, 나중에 하위 창을 손대다 중하·중위로 새면
즉시 깨진다.

### 4.2 실측: 하위 96시드 전부 96/96 (base·expose 양쪽)

참조봇 `autopilot` · `GEAR_REFERENCE` 고정 장비 · 96시드(ADR-0037 튜닝 스윕 해상도).
**대조군(base)과 실험군(expose)을 같은 6세대 sim 에서 각각 돌렸다** — 리베이스로 sim 이
바뀌었으므로 이전 세대의 base 값을 인용하지 않고 다시 쟀다.

| nn | base (96시드) | expose (96시드) |
|---|---|---|
| #01 | 100.00 (96/96) | **100.00** (96/96) |
| #02 | 100.00 (96/96) | **100.00** (96/96) |
| #03 | 100.00 (96/96) | **100.00** (96/96) |
| #04 | 100.00 (96/96) | **100.00** (96/96) |
| #05 | 100.00 (96/96) | **100.00** (96/96) |
| #06 | 100.00 (96/96) | **100.00** (96/96) |
| #07 | 100.00 (96/96) | **100.00** (96/96) |
| 하위 밴드 | **100.00** | **100.00** |

즉 `heavyrail`(피해 40) · `siegecannon` · `demolisher`(해저드 23) 같은 Lane9 최상위 화력이
하위 기지에 서도 **하위 난이도를 밀어 올리지 않는다**. 복원 레인이 중위에서 관측한 "신규 8종의
실효 화력이 기존 0~8 과 비슷하다"가 하위 레벨대(1..10 · rarity 0 · ascension 0)에서도, 그리고
판정이 세진 6세대 sim 에서도 성립한다.

여유 15pp 를 쓰지 않았으므로 **상쇄 조정이 필요 없었다**. 상쇄가 필요했다면 하위 전용 축
(레벨 기울기·기물 충전량)을 썼을 것이나, 실측이 그 필요를 없앴다.

⚠️ **바닥·천장에 붙은 지표는 변화를 못 보여준다는 한계**를 기록해 둔다. 하위는 base 도
100.00% 라 "안 나빠졌다"까지만 실측이고 "얼마나 안 나빠졌는가"는 이 측정으로 알 수 없다.
하위 목표가 "85+"(상한 없음)라 실용적으로는 충분하지만, 훗날 하위 밴드를 천장에서 내리는
레인이 오면 **그 시점에 이 노출을 다시 재야 한다**.

### 4.3 `#16` 확인

`#16` 은 nn=16 → `nn <= 7` 분기 밖이라 **이 레인이 만드는 배치가 바이트 동일**하다.
따라서 6세대 24시드 20.83%(5/24) 가 그대로이고 "클리어 불가 기지 없음" 불변식이 유지된다.
96시드로 재측정할 필요도 없다 — 입력이 같으면 결정론(ADR-0005)상 출력이 같다.

## 5. 커버리지 테스트 복원 — 이 레인의 진짜 완료 신호

`20기지가 시드 램프 목표 카탈로그를 전부 노출한다(미사용 시드 콘텐츠 0)` 는 종전에
**편대·설비만 "램프 상한까지"** 라는 약한 형태였다:

```ts
const seedFacilityKinds = Math.max(...Array.from({length: 20}, (_, i) => RAMP.facilityKinds(i + 1)));
expect([...facilities].sort(...)).toEqual(Array.from({length: seedFacilityKinds}, (_, i) => i));
```

기대값을 **램프에서 파생**시키므로 램프가 뒤를 잘라도 통과한다 — 재려던 것("만든 콘텐츠가 다
보이는가")을 못 재는 형태였다. 이제 네 축 모두 카탈로그 전량을 요구한다:

```ts
expect([...formations].sort(...)).toEqual(FORMATIONS.map((_, i) => i));
expect([...facilities].sort(...)).toEqual(INVASION_FACILITIES.map((_, i) => i));
expect([...props].sort(...)).toEqual(L3_PROPS.map((_, i) => i));
expect([...bosses].sort(...)).toEqual(DEFENSE_BOSSES.map((_, i) => i));
```

**복원 완료.** 카탈로그에 종을 append 하고 램프를 안 열면 이제 이 단언이 먼저 깨진다.

다만 하위 창 크기가 SQL 에 상수로 박혀 있어(`c_form_len` 12 · `c_fac_len` 17) 커버리지 단언만으로는
"SQL 을 안 고쳤다"를 특정하기 어렵다. 그래서 진단용 단언을 하나 더 뒀다 —
`하위 밴드 창 크기가 카탈로그 길이와 같다`. `RAMP.*Kinds(1)` == 카탈로그 길이 + SQL 안의
상수 선언 문자열까지 대조한다.

1회차에 이미 정상 적용됐고(멱등이라 2회차 재실행도 무해), 스크립트를 고쳐 재실행해 통과했다.
**교훈: 램프를 바꿀 때 고쳐야 하는 자리는 SQL 본문·RAMP 주석·테스트 미러 셋이 아니라
"적용 스크립트의 기대값"까지 넷이다.**

214.93KB. 업로드 자산이 `deno.json` + `index.ts` **둘뿐**(치환이 제대로 됐다는 방증).

부팅 스모크: anon 인증으로
`400 {"status":"rejected","reason":"malformed-invasion-id","attackerWon":false,...}` 확인 +
그 문자열이 배포 번들에 **정확히 1회** 존재 — 게이트웨이가 아니라 우리 코드가 실행됐다.

⚠️ **배포 명령의 cwd 는 번들 워크트리 루트여야 한다.** 1회차에 본 작업 워크트리 루트에서
`spb functions deploy` 를 돌려 CLI 가 **번들이 아닌 원본 `index.ts`** 를 entrypoint 로 잡았고,
sloppy-import 해석 실패로 `400 Module not found ".../verify-run/verifyCore.js"` 가 났다.
(잘못된 번들이 올라간 것이 아니라 배포 자체가 거부됐다 — 라이브는 안전했다.)
절차 문서가 경고하는 "cwd 가 함수 디렉터리면 실패" 와 **다른 실패 방식**이다:
그쪽은 entrypoint 경로가 아예 없다는 400 이고, 이쪽은 경로가 **존재하되 다른 워크트리의 원본**
이라 조용히 잘못된 파일을 집는다. 후자가 더 위험하다 — **배포 로그의 "Uploading asset" 목록에
`verifyInvasionCore.ts` 가 보이면 잘못된 entrypoint 를 집은 것**이니 그 신호로 판별해라.
