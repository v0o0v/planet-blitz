## 1. 구조 설명 — AI 가 감당할 수 있게 설계한 아키텍처

AI 에게 대량의 코드를 맡길 때 가장 큰 위험은 "그럴듯하지만 틀린 코드"입니다. 이 프로젝트는
아키텍처 자체를 **기계 검증이 가능한 형태**로 설계해 그 위험을 구조적으로 눌렀습니다.

```
[결정론 시뮬 코어 src/sim]  ←  순수 TS · 시드 RNG 전용 · 렌더/시간/난수 API 금지 (ESLint 강제)
        │ 스냅샷
[렌더 계층 PixiJS v8]        ←  시뮬에 역류 불가 — 화면 버그가 게임 로직을 오염 못 함
        │ [시드 + 입력로그] 리플레이
[서버 Supabase]              ←  결정론 재실행으로 런 결과를 검증 — 클라 위조 불가
```

- **결정론이 곧 테스트 가능성**: 같은 시드 → 같은 결과가 보장되므로, "AI 가 고친 코드가
  게임 결과를 바꿨는가"를 틱 단위 상태 해시 비교로 기계가 판정합니다. 사람이 눈으로 확인할
  필요가 없어 AI 의 대량 산출을 받아낼 수 있습니다.
- **규율은 부탁이 아니라 lint**: 시뮬 코어의 `Math.random`·`Date.now`·`pixi.js` import 는
  ESLint 에러입니다. AI 가 실수해도 커밋 전에 기계가 막습니다.
- **서버 권위**: 드랍·의뢰·래더 스왑 등 보상 쓰기는 Edge Function + RLS 로 서버만 수행 —
  AI 가 짠 클라이언트를 신뢰하지 않는 전제로 온라인 게임을 성립시켰습니다.

## 2. AI 디렉팅 파이프라인 — 사람은 무엇을 했는가

### 2-1. 설계: 인터뷰로 확정하고, ADR 로 고정한다

- 개발 첫날 AI 와의 **딥 인터뷰**(12~14라운드)로 게임 설계 문서(GDD)를 확정 — AI 가
  모호점을 소크라테스식으로 추궁하고, 사람이 결정하고, 결과가 `docs/GDD.md` 로 남습니다.
- 되돌리기 어려운 결정은 **ADR**(Architecture Decision Record) 55건으로 고정. AI 세션은
  매번 새로 시작되므로, "왜 이렇게 했는가"를 리포에 적어 두는 것이 AI 의 장기 기억입니다.

### 2-2. 실행: 병렬 레인 + 작성자/비평자 분리

- 작업은 **git worktree 로 격리된 병렬 레인**에서 진행 — 동시에 여러 AI 세션이 서로 다른
  기능(스킬 210종 상세, 촉매 배선, 침공 HUD…)을 각자 브랜치→PR 로 진행했습니다.
- 한 레인 안에서도 역할을 나눈 서브에이전트를 씁니다: 탐색(explore) → 계획(planner) →
  구현(executor) → **비평(critic)** → **검증(verifier)**. 특히 **작성자가 자기 결과를
  승인하지 못하게** 별도 컨텍스트의 비평자가 결함을 적발합니다 — 이 루프가 반복 적발한
  결함 패턴(예: 항진 명제 테스트, 하드코딩 답습)은 문서로 축적해 다음 레인의 지시에 반영했습니다.

### 2-3. 검증: AI 산출물은 게이트를 통과해야 한다

- **3단 검증 규약**(리포 `CLAUDE.md` 정본): 편집 중 짝 테스트(~7초) → 커밋 전 변경분
  테스트(~34초) → PR 전 전체 스위트+타입+린트(~90초). AI 에게 이 규약 자체를 지시문으로
  주어, 매 편집이 게이트를 통과해야 다음으로 갑니다.
- **결정론 게이트**: 대표 행성×빌드 조합을 같은 시드로 두 번 돌려 해시가 원소 단위로 같은지
  상시 검사 — "골든 상수와 같은가"가 아니라 "자기 자신과 같은가"를 재서 유지비 없이
  재현성을 지킵니다.
- **밸런스 계측 CLI**: 클리어율·도달 틱·드랍량을 결정론 봇으로 일괄 계측(`bench/`) —
  AI 가 수치를 바꾸면 사람이 감이 아니라 표로 판단합니다.

### 2-4. 지식 축적: 실패를 다음 지시에 되먹인다

세션이 끝날 때마다 "무엇이 틀렸고 왜"를 메모리 파일로 남겨 다음 세션의 컨텍스트에 주입
했습니다. 예: *"파이프가 exit code 를 덮어 거짓 초록을 만든다"*, *"골든 재생성은 검증이
아니다 — 다시 뜬 값으로 그 값을 검사하면 항진이다"*. 같은 실수를 두 번 하지 않게 하는
이 되먹임이 26일 완주의 실질 동력이었습니다.

## 3. 주요 프롬프트·지시 사례 (전부 실물 — ①~③은 게임 리포, ④는 에셋 라이브러리 기록)

**① 검증 규약을 지시문으로** — 리포 `CLAUDE.md` (모든 AI 세션에 자동 주입):

> "전체 스위트를 편집 한 건마다 돌리지 않는다. 실측으로 비용 차이가 34배다. 편집 중:
> 고친 것의 짝 테스트(약 7초) / 커밋 전: `pnpm test:changed`(약 34초) / PR 전:
> `pnpm verify`(약 1분 30초). `pnpm verify` 를 파이프에 물리지 마라(`| tail` 금지) —
> exit code 가 `tail` 것이 되어 거짓 그린이 된다."

**② 검증의 원칙을 원칙 문장으로** — 같은 문서:

> "골든 재생성은 검증이 아니다. 다시 뜬 값으로 그 값을 검사하면 항진이다. (…) 이 파일은
> 골든 상수를 갖지 않는다 — 모든 단언이 '같은 입력을 두 번 돌린 결과끼리' 비교다."

**③ 결함을 사양으로 박제** — ADR-0051 (테스트 축을 게이트에서 내리며):

> "단언이 '봇이 이길 수 있는가'에 의존하면 게이트에서 내린다. 대신 배선 증명은 내구
> 파일럿 + 최소 틱으로 다시 써서 살렸다 — 삭제로 도망친 게 아니다."

**④ 에셋 생성 프롬프트** — PixelLab 픽셀아트 생성 로그(에셋 라이브러리 인덱스에 974건
축적, 각 항목에 프롬프트·라이선스·해시 기록). 실제 항목 예:

> `pb_berdan_charger` — prompt: `insectoid darting larva charger` (top-down · 64px) /
> `pb_berdan_gunner` — prompt: `insectoid spitting soldier` — 행성별 적 테마(베르단 =
> 군체 곤충)를 짧은 프롬프트 어휘로 통일해, 573장이 한 게임의 그림처럼 보이게 했습니다.
