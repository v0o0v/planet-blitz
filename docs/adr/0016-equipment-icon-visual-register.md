# 장비·스킬 아이콘은 세 번째 시각 레지스터를 갖는다 (앵커 `pb-equip-icon`)

ADR-0015 가 아이콘 축(무엇이 같으면 같은 그림인가)을 정하면서 시각 레지스터 선택은 "샘플 대조로 실증한 뒤 기록한다"고 미뤄 뒀다. 이 프로젝트엔 이미 두 시각 언어가 있다 — 메타 화면의 **카툰나무풍**(`pb-cartoon-wood-ui` 앵커, 22장)과 전투 화면의 **SF 픽셀아트**(적·보스·포탑·기체 60여 장, 앵커 이전 자산). 장비 아이콘은 나무 슬롯 프레임 **안에** 들어가지만 내용물은 기체에 달리는 SF 장비라 둘 사이에 놓인다. 결정: **어느 쪽에도 편입시키지 않고 새 앵커 `pb-equip-icon` 을 세운다.** 정본은 `pb_equip_style_anchor_sheet` (pixellab-forge `library/`) 이고, 스타일은 소프트 카툰 픽셀아트 — 고디테일, 크림/골드 림라이트, 무거운 다크 아웃라인 없음.

세 후보를 실물로 만들어 1920 폭 대조 페이지에서 판정했다(실제 `ui_slot.png` 셀 안 64px + 4배 확대 + 기존 `ui_icon_*` 옆에 나란히). **A 하이브리드·두꺼운 아웃라인** / **B 하이브리드·아웃라인 제거** / **C SF 월드톤**. 대조군은 레일건(무기 실루엣 판독)·실드(추상 개념)·과열 드럼(유니크 고유 아트) 세 축으로 골랐다. 채택은 **B**.

C 를 기각한 이유는 취향이 아니라 **일관성 구조**다. C 는 REST 낱장 독립 생성이라 표본 3장에서 이미 톤이 갈렸다(레일건은 어둡고 저채도, 드럼은 붉게 튐). 77장으로 늘리면 이 편차가 누적되고, 막으려면 매 호출에 `style_images` 앵커를 물리는 수동 관리가 영구히 따라붙는다. 반면 MCP 로 한 시트에 3아이콘을 함께 뽑으면 한 팩 안에서 **시트 내부 톤이 자동으로 정렬**된다. A 와 B 의 차이는 흥미롭게도 지시대로 되지 않았다 — 프롬프트로 아웃라인 제거를 명시했지만 생성기는 여전히 경계선을 그렸고, 실제로 달라진 것은 디테일 밀도와 채도였다. 사용자 검수는 그 상태의 B 를 채택했다.

## 결정 사항

- **앵커는 `pb-equip-icon`.** 카툰나무풍 UI 킷(`pb-cartoon-wood-ui`)과 **섞지 않는다** — UI 크롬(버튼·패널·자물쇠)과 게임 사물(레일건·실드)은 다른 종류이고, 한 앵커로 묶으면 이후 생성에서 서로의 문법을 오염시킨다.
- **생성 단위는 낱장이 아니라 시트. 도구는 `create_1_direction_object`(size 512) + `item_descriptions` 배열 3개다.** 한 팩 안에서 톤이 자동 정렬되는 것이 이 방식을 고른 이유이고, 그 이유는 도구가 바뀌어도 그대로 성립한다 — 세 아이콘이 한 번의 생성에서 함께 나오기 때문이다. 77장이면 26시트다. 이 ADR 은 처음 `create_ui_asset` 512×192 라고 적었지만 두 가지가 틀렸다. 첫째, 정본 `pb_equip_style_anchor_sheet` 가 실제로 쓴 도구가 `create_1_direction_object` 였다. 둘째, `create_ui_asset` 을 확인차 돌려 보니 `pieces`(rounded_rect)가 칸마다 크림색 라운드 사각 테두리를 구워 넣었다 — `radius: 0` 과 description 의 "no panel frame" 지시가 **둘 다 무시**됐다. 이 테두리는 슬라이싱의 알파 바운딩박스에 섞여 그림 대신 프레임을 기준으로 잘라내므로 아이콘이 쪼그라든다. 파이프라인을 깨는 결함이라 취향 문제가 아니다.
- **슬라이싱은 알파 바운딩박스 + 비율 유지.** 시트를 균등 분할한 뒤 각 칸에서 `getbbox()` 로 실제 그림만 잘라내고, 가로세로 비율을 유지한 채 64×64 캔버스 중앙에 nearest 로 배치한다(안쪽 여백 2px). 비율을 무시하고 늘리면 픽셀아트가 뭉개진다.
- **가로로 긴 물건은 대각선 지향으로 생성한다.** 레일건은 134×49 로 나와 64px 칸에 맞추면 60×21 이 되어 칸의 3분의 1만 채웠다. 무기류가 대부분 이 형태이므로 프롬프트에 대각선 방향을 명시한다 — 생성 시점 수정이라 추가 비용이 없다. (RPG 인벤토리가 무기를 눕히는 것이 같은 이유다.) 효과는 실측으로 확인됐다: 같은 레일건이 정본에서 60×22 로 칸의 **34%** 를 채웠는데, 대각선 지향을 넣은 v2 는 60×47 로 **68.8%** 가 됐다.
- **기각 후보도 캐시에 남기되 앵커를 주지 않는다.** `rejected-probe` 태그로만 등록해 유실은 막고 `find --anchor pb-equip-icon` 결과에는 섞이지 않게 한다.

## Consequences

- **시각 레지스터가 셋이 된다.** 카툰나무풍(UI 크롬) · `pb-equip-icon`(게임 사물 아이콘) · SF 픽셀아트(전투 화면). 앞의 둘은 같은 화면에 동시에 보이므로 나란히 놓았을 때의 정합이 계속 검증 대상이다. 셋째가 늘어나는 것을 막으려면 새 아이콘은 반드시 기존 세 앵커 중 하나에 배정한다.
- **재생성 단위가 시트다.** 아이콘 하나만 고치고 싶어도 같은 시트의 3개가 함께 다시 나온다. `seed` 고정이 구도를 어느 정도 붙잡아 주지만 완전하지 않다. 시트를 짤 때 **함께 수정될 법한 것끼리 묶는다**(같은 스탯의 티어 3단계를 한 시트에 두는 식). **(Lane 10)** 스킬 티어대가 3구간 → 5구간(low·lowmid·mid·midhigh·high)으로 넓어져 스탯당 아트가 3장에서 최대 5장이 됐다. 기존 low/mid/high 아트는 보존되고 신규 `lowmid`·`midhigh` 만 후속 생성 대상이라, 이 둘을 한 시트(2아이콘)로 묶어 뽑으면 같은 스탯 안에서 톤이 이웃 밴드와 정렬된다.
- **비용은 제약은 아니지만 무시할 수준도 아니다.** 실측 — REST pixflux 64px $0.0059~0.0062/장, MCP 시트는 3시트에 $0.36~0.38 이 빠져 **시트당 약 $0.12**(아이콘 1장당 약 $0.04)다. 77장 환산은 각각 $0.46 / **약 $3.1** 이라 REST 낱장보다 오히려 비싸고, 그래도 시트를 고르는 이유는 값이 아니라 톤 정렬이다. 이 ADR 은 처음 "25 generations 는 잔액 차감이 센트 표시 아래(≲$0.003)"라고 적었는데 실측과 40배가 어긋났다 — 무료 generation 할당이 남아 있던 구간의 관측을 단가로 오해한 것이고, 할당이 소진된 뒤로는 크레딧에서 직접 차감된다. 설계 논의 초반의 "MCP 경로로는 잔액 초과"도 generations 를 장당 이미지 단가로 곱한 별개의 **오산**이었다. 즉 같은 항목을 양방향으로 두 번 틀렸다. **추정하지 말고 `get_balance` 전후 차이로 잰다**는 원칙은 이 ADR 이 이미 옳게 적어 뒀는데도 틀린 수치가 그대로 남아 있었다 — 원칙을 적는 것과 매번 실행하는 것은 다르다.
- **아웃라인이 얇아 어두운 셀 바탕에서 경계가 약할 수 있다.** 기존 `ui_icon_*` 16종은 두꺼운 다크 아웃라인을 쓰므로 나란히 놓이는 구간에서 이질감이 생길 여지가 있다. ADR-0015 가 정한 등급색 글로우가 장비 슬롯에서는 이를 일부 상쇄하지만, 스킬 노드처럼 글로우가 없는 곳은 실화면 검증에서 따로 본다.
- **크기로는 티어 차이를 전달할 수 없다.** 슬라이서가 알파 bbox 로 잘라낸 뒤 비율을 유지한 채 60px 까지 **확대**하므로, 원본 시트에서 칸 점유가 5.8% / 29.9% / 65% 로 크게 벌어져 있던 세 아이콘이 최종 64×64 에서는 82% / 85% / 86% 로 거의 같아진다. "고티어는 크게 그린다" 같은 지시는 파이프라인을 통과하면서 지워진다는 뜻이다. 티어 차이는 크기가 아니라 **형태·장식·색**으로 그려야 하고, 반대로 원본이 작게 나와도 최종 결과는 멀쩡하다. 후속 아이콘 시트를 짤 때 이 성질을 전제로 프롬프트를 쓴다. **(Lane 10)** 5구간 확장으로 이 요구가 더 커졌다 — 이제 한 스탯이 최대 5밴드라 인접 밴드(예 low↔lowmid, mid↔midhigh)가 크기로는 전혀 안 갈리므로, 신규 `lowmid`/`midhigh` 아트는 이웃 밴드와 **형태·장식·색의 중간 단계**로 그려 순서가 읽히게 해야 한다.
- **시트 슬라이싱이 자산 파이프라인의 새 단계가 된다.** 아이콘을 다시 뽑을 때마다 필요하므로 리포에 둔다. 다만 기존 `scripts/asset-prep.mjs` 는 **의존성 0**(Node 내장 `zlib`/`fs` 로 PNG 를 직접 디코드·인코드)을 명시적 규약으로 삼는다 — 슬라이싱도 같은 규약으로 그 파이프라인 안에 넣는다. 알고리즘 검증은 Pillow 프로토타입으로 끝냈지만(알파 bbox + 비율 유지 축소 + 중앙 배치가 의도대로 동작함을 확인), Python 의존을 리포에 들이지는 않는다.
