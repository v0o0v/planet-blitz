# ADR-0038 — 행성 인기 기반 보상 배율

- 상태: 채택 (2026-07-27)
- 관련: ADR-0022(침략 단계가 티어를 대체 · 품질⟂종류 직교) · ADR-0027(재화 서버 원장) ·
  ADR-0029(촉매) · ADR-0035(표준 진행 경로) · ADR-0036(경험치 이원화)

> ⚠️ 번호 주의: 이 저장소에는 `0029`·`0034` 가 각각 **두 개씩** 있다(과거 병렬 레인 충돌).
> 다음 ADR 은 **0039** 부터 잡되, 먼저 `ls docs/adr/` 로 중복 여부를 확인할 것.

## 맥락

행성 6종은 서로 다른 **행성 모드**(뱀서류·블록격파·레이싱·추격·수축·오염)와 특산 설계도·특산
광물을 갖지만, 보상 **기댓값**은 사실상 동일하다. 그 결과 플레이어는 자기에게 가장 쉬운(또는
가장 짧은) 행성 하나를 골라 반복하게 되고, 나머지 5종은 구현·아트·밸런싱 비용을 치른 채 거의
소비되지 않는다. 실제로 어떤 행성이 편식될지는 사전에 알 수 없고, 패치마다 바뀐다.

정적 계수(예: "톡사르는 항상 ×1.1")로는 이 문제를 못 푼다 — 계수 자체가 새로운 최적해를 만들
뿐이고, 편식 대상이 바뀔 때마다 사람이 재조정해야 한다.

## 결정

**전체 유저 통계 기준으로 덜 도는 행성의 보상을 올리고 많이 도는 행성의 보상을 내리는 자동
평형 장치를 도입한다.**

| 갈래 | 결정 |
|---|---|
| 입력 변수 | **전체 유저 통계** (per-player 아님) |
| 집계 지표 | 행성별 **PvE 런 정산 건수** |
| 윈도우 / 갱신 주기 | 최근 **1시간** 창, **30분**마다 갱신 |
| 댐핑 | 사전표본 `K` + 지수평활 `α` |
| 보상 축 | **XP · 아이템 수량 · 자원** |
| 불가침 축 | **품질(rarity)** — ADR-0022 계약 그대로 |
| 산식 | 역비례 → 클램프 → 런가중 재정규화 → 지수평활 |
| 가시성 | 성계 지도에 **실수치 상시 노출**(`보상 ×1.12`) |
| 적용 레이어 | **sim** — 런 시작에 `runConfig` 스탬프 |
| 기존 배율 합성 | **그냥 곱** (상한 캡 없음) |
| 오프라인·미로그인·미설정 | **전 행성 1.0** |
| 어뷰징 방어 | 없음 (단, 계정별 기여 카운트는 집계 테이블에 남긴다) |

### 산식

```
ŵᵢ        = (cᵢ + K) / (R + 6K)                       # 사전표본 축소. cᵢ = 행성 i 런 수, R = 총합
mᵢ_raw    = (1/6) / ŵᵢ                                 # 역비례
mᵢ_clamp  = clamp(mᵢ_raw, CLAMP_LO, CLAMP_HI)
mᵢ_target = mᵢ_clamp / Σ(wᵢ · mᵢ_clamp)                # 런가중 재정규화 → Σwᵢmᵢ = 1
mᵢ_new    = mᵢ_prev + ALPHA × (mᵢ_target − mᵢ_prev)    # 지수평활
```

- **사전표본 `K`** 는 표본이 적을 때 배율이 1.0 에 붙게 만든다. 출시 직후처럼 R 이 작으면
  노이즈가 그대로 배율로 증폭되는데, `K` 가 그 구간을 통째로 죽인다.
- **런가중 재정규화**가 `Σ(wᵢ · mᵢ) = 1` 을 세운다 — **현재 플레이 분포로 가중한 평균 배율이
  정확히 1**이라, 배율 도입이 게임 전체 보상 총량을 늘리거나 줄이지 않는다. 개별 행성만
  오르내린다. (클램프가 재정규화 **앞**에 오므로 최종값은 클램프 경계를 조금 넘을 수 있다 —
  총량 불변이 경계 엄수보다 중요하다는 판단이다.)
- **지수평활 `α`** 는 한 주기 갱신이 배율을 급변시키지 않게 한다. 30분마다 표가 튀면 플레이어가
  "지금 도는 행성"을 계속 바꾸게 되고, 그건 균일 소비가 아니라 산만함이다.

### XP 하한 재적용

`최종 XP 배율 = max(0.30, 저단계감쇠 × 행성배율 × 촉매xp × loadout.xpMult)`

ADR-0035 의 30% 안전망은 "이 런의 XP 효율이 **어떤 조합에서도** 30% 밑으로는 안 간다"는 약속
이다. 축 하나가 아니라 **합성 결과**에 걸려야 하므로, 두 인자가 모두 보이는 정산 레이어에서
되푼다(`src/save/settlement.ts` `xpAppliedPercent`).

### 배율이 닿지 않는 곳

| 대상 | 이유 |
|---|---|
| **품질(rarity)** | ADR-0022 "품질은 전 행성 동일"이 계약. 행성별 유니크 편차 = 심층 사다리 부활 |
| **보스 확정 드랍 1개** | ADR-0035 확정성 계약. "사망 페널티 = 보스 보상 상실"이 여기 걸려 있다 |
| **특산 설계도 · 특산 촉매** | 원칙: **대체 가능한 보상에만 배율.** 특산은 그 행성에서만 나오므로 대체 불가 |
| **조우 보상** | 보물 격실·봉인 수호자·오스카 제단·기록 파편우·유령 보급선단 — 조우는 행성 선택의 이유가 아니라 런 안의 사건이다 |
| **침공(PvP) · 예비역 소집** | 행성 파밍 축이 아니다. `designedRun` 분기로 자동 격리 |
| **하네스 · 오염 런** | 정산 스킵(ADR-0008) |

**특산 설계도 역수 보정**: 수량 배율이 엘리트 드랍 **건수**를 ×m 으로 바꾸면 설계도 기대
획득량도 자동으로 ×m 이 된다. 그래서 **엘리트 유래 레코드의 동반 확률만 ×(1/m)** 로 되돌린다
(`LootRecord.elite` 표식으로 보스 몫과 구분 — 보스까지 보정하면 오히려 ∓m 만큼 틀어진다).

> ### ⚠️ SUPERSEDED — 위 역수 보정은 철거됐다 (2026-08-08)
>
> **지키려던 불변("특산 설계도 기대 획득률은 인기 배율 밖")은 그대로 유효하고, 수단만 바뀌었다.**
> 설계도가 **런 단위 3% 게이트**(`BLUEPRINT_RUN_CHANCE_CP`)로 바뀌면서 획득률이 드랍 건수와
> **구조적으로 분리**됐다 — 드랍이 2건이든 20건이든 런당 3% 다. 즉 배율이 건수를 ×m 해도
> 획득률이 애초에 움직이지 않으므로 되돌릴 것이 없다.
>
> 보정을 남겨 두면 이제는 기대 획득량이 아니라 **엘리트 대 보스의 추첨 비중만** 근거 없이
> 틀어놓는다. 그래서 `blueprintDropsFromLoot` 는 **배율 인자를 아예 받지 않는다** — 불변이
> 통계적 근사(구 테스트는 오차 15% 를 허용해야 했다)에서 **시그니처가 보장하는 항등**이 됐다.
>
> `LootRecord.elite` 표식은 계속 스탬프되지만 **설계도 축은 더 읽지 않는다.**

## 파생 결정

### centi 정수

배율을 **0.01 단위 정수**(중립 `100`)로 저장·전송·해시한다. 리포의 `blueprintChanceCp`
(centi-percent) 관례와 정합하고, EF(Deno)↔브라우저 IEEE754 재현 논쟁을 제거한다.
`100 / 100 === 1` 이 IEEE754 에서 정확하므로 **중립 런의 곱셈은 무연산**이다.

### 조건부 해시 폴드

`hashWorld` 는 `planetMultCenti !== 100` 일 때만 접는다. 그래야:
- 침공 런·기존 골든이 **바이트 불변**이고,
- **`verify-invasion` EF 재배포가 불필요**하다.

조건부 폴드 선례는 `shipType`·`planetMode`·촉매 꼬리에 있다. `planetMultEpoch` 은 sim 이 읽지
않는 순수 메타(`runId` 와 같은 성격)라 접지 않는다.

### 행성 단위이지 행성×단계 단위가 아니다

단계1 카르곤과 단계20 카르곤은 **같은 배율**이다. 단계는 이미 ADR-0022 의 독립 축이고, 배율을
단계까지 쪼개면 "어느 단계를 도는가"까지 배율이 지시하게 돼 단계 선택의 자유가 줄어든다.

### epoch 스탬프 + 서버 권위

`epoch`(30분 단위 정수)을 `runConfig` 에 함께 스탬프하고, 정산 `p_summary` 로 서버에 보낸다.
**클라는 배율값 자체를 보내지 않는다** — 서버가 그 epoch 의 **자기 스냅샷**을 읽는다.

서버의 역할은 **권위이지 재적용이 아니다**. sim 이 이미 배율을 적용해 자원을 적립했으므로,
서버가 또 곱하면 이중 적용이다. 서버는 그 배율만큼 **지급 상한(개연성 캡)을 넓혀**, 정직한
클라의 정당한 주장이 클램프되지 않게 한다. 이는 촉매 `resource_mult` 영수증이 캡을 상향하는
규율과 **동일**하고, 따라서 **추가 RPC 가 0**이다. epoch 이 현재/직전이 아니면 1.0 취급이라
오래된 고배율 스냅샷을 재사용할 수 없다.

### 클라 폴링은 출격을 블로킹하지 않는다

배율표는 30분 주기로 폴링해 캐시하고, 런 시작에는 **동기 캐시 리더**로 읽는다. 이 저장소는
"촉매가 있을 때만 서버를 부르고, 없으면 서버 없이 출격한다"는 성질을 의도적으로 보존해 왔다
(`src/main.ts` `beginSortie`) — 배율 도입이 그 성질을 깨서는 안 된다. 폴링 실패·미설정·미로그인은
전부 전 행성 1.0 폴백이다.

## 기각한 대안

| 대안 | 기각 근거 |
|---|---|
| **per-player 카운트** | "내가 많이 돈 행성이 나에게만 나빠진다" = 플레이어 개인을 벌하는 구조. 좋아하는 행성을 계속 돌 자유를 뺏고, 최적 플레이가 "싫어하는 행성 로테이션"이 된다. 목표는 개인 강제가 아니라 **전체 분포 평탄화**다 |
| **고유 플레이어 수 지표** | 헤비 유저 1명과 라이트 유저 1명이 같은 가중치가 된다. 우리가 평탄화하려는 것은 **소비량**(런 수)이지 인구가 아니다. 계정 생성 비용이 0 이라 위조도 더 쉽다 |
| **정적 행성 계수** | 계수 자체가 새 최적해를 만들 뿐이고, 편식 대상이 바뀔 때마다 사람이 재조정해야 한다. 자동 평형이 아니다 |
| **정산 레이어 적용** | 런 중에는 배율이 안 보이다가 결과 화면에서만 튀어나온다 — 플레이어가 "이 런이 왜 이만큼인지"를 실시간으로 연결하지 못한다. sim 적용은 드랍 수·XP 가 **런 중에** 눈에 보인다. 또 정산 적용은 리플레이 재검증 대상 밖이라 위조 표면이 넓다 |
| **보너스 전용(하향 없음)** | 상향만 하면 전체 재화 유입이 단조 증가한다(경제 총량 불변이 깨진다). 그리고 "덜 도는 행성이 이득"만 있고 "많이 도는 행성이 손해"가 없으면 편식 행성을 떠날 이유가 약하다 |
| **가산 합성(`+0.2` 식)** | 촉매·loadout 이 전부 곱셈 축이라 혼자 가산이면 합성 결과가 직관에서 벗어난다. 곱은 "축이 서로 독립"이라는 기존 모델과 정합 |
| **어뷰징 방어** | 배율 상한이 `CLAMP_HI` 로 유계라 최대 이득이 작고(≈ +20%), 조작하려면 **전체 유저 통계**를 움직여야 해서 봇 다수가 필요하다. 비용 대비 이득이 낮아 1차 출시 범위에서 제외한다. 다만 집계 테이블에 **계정별 기여 카운트**(`contributors`·`top_contributor_runs`)를 남겨 **소급 판단**은 가능하게 한다 |

## 귀결

- **밸런스 상수는 전부 플레이스홀더다** — `CLAMP_LO 0.85` · `CLAMP_HI 1.20` · `K 80` · `α 0.2`.
  값 결정·스윕·실측 튜닝은 출시 직전 일괄 밸런스 패스로 미룬다.
- **수량 합성에 상한이 없다** — 행성 1.20 × 촉매 2.2 = ×2.64 유입이 가능하다. 이 조합의 재보정은
  밸런스 큐다. `tests/drops.test.ts` 의 "런당 장비 유입" 가드는 **배율 1.0 기준으로 명시 고정**해
  두었다.
- **점유율 목표치(max/min 비 ≤ 1.5 등)를 CI 게이트로 만들지 않는다** — 지표는 스냅샷 테이블에
  쌓이므로 관측은 가능하다. 게이트화는 밸런스 판단이라 이 축의 결정이 아니다.
- **산식이 이중 구현이다** — `src/economy/planetPopularity.ts`(정본·단위 테스트)와
  `supabase/migrations/20260727010000_planet_popularity.sql`(실제 30분 갱신). **항상 같은
  커밋에서** 고칠 것. 갈리면 서버가 이기고 클라 표시가 틀린다.

### 구현 중 드러난 결함 하나 (기록)

지수평활을 centi **정수** 격자에서 돌리면, 목표에 가까워질수록 한 주기 스텝
(`α × |target − prev|`)이 0.5 centi 밑으로 내려가고 그 순간 반올림이 결과를 `prev` 로 되돌려
**영원히 멈춘다**. 목표에 2 centi 못 미친 채 "수렴한 척"하며, 그 상태에서 `Σwᵢmᵢ = 1` 불변식이
1.019 로 깨진다. §1 런가중 평균 테스트가 이걸 잡았다. 보정은 "목표가 1 centi 이상 남았는데
반올림이 제자리면 최소 1 centi 전진"이다 — **TS·SQL 양쪽에 다 들어가 있다**.
