# ADR-0041 — 액티브 스킬: 기체 타입 고유 · 트리 게이트 · 플레이어 전용

- 상태: 채택 (2026-07-31)
- 관련: ADR-0019(기체 타입 고유 트리) · ADR-0005(sim 결정론 경계) ·
  ADR-0015(아이콘 축은 속성) · ADR-0025(수호 기체는 실물 빌드에서 파생) ·
  ADR-0026(PvE 는 리플레이 미제출) · ADR-0030(장비 요구 레벨 게이트)

## 맥락

이 게임에는 **플레이어가 키로 발동하는 능력이 사실상 없다**. 대시(Space) 하나뿐이고,
나머지 전부 — 시그니처 패시브·유니크·캡스톤·파워업·촉매·장비 어픽스 — 는 켜두면 알아서
도는 패시브다. 전투는 이동과 회피로만 이뤄지고, 자동공격이 딜을 담당한다.

그 결과 **기체 타입 7종의 차이가 조작에서 드러나지 않는다**. 트리와 시그니처 패시브가
수치로는 갈라놓지만, 손끝에서 다르게 느껴지지 않는다 — ADR-0019 가 "LoL 챔피언에 해당하는
선택 단위"라고 못 박은 것에 비하면 체감이 빈약하다.

동시에 이 저장소에는 **신중해야 할 이유**가 셋 있다.

1. `InputFrame` 은 리플레이 wire 이고, 침공은 서버(`verify-invasion` EF)가 전수 재실행으로
   검증한다(ADR-0005). 입력에 무엇을 더하든 그건 포맷 변경이다.
2. 침공 난이도는 96시드 계측으로 밴드(100.00 / 70.83 / 40.28)에 겨우 앉혀놓은 상태다.
   방어측 전력이 바뀌면 그 기준선이 통째로 무효가 된다.
3. 성장 축이 이미 셋(스킬트리 투자 · 장비 파밍 · 계보)이고, 만렙 기체는 **퇴역**으로
   주기적으로 리셋된다. 네 번째 해금 축을 얹으면 세대 교체 비용이 급등한다.

## 결정

**액티브 스킬을 신설한다 — 기체 타입마다 6종, 계열 투자로 열리고, 플레이어만 쓴다.**

### 왜 6종인가 (5종이 아니라)

원 요청은 기체당 5종이었으나 **트리가 3계열**이라 5는 나눠지지 않는다. 2/2/1 로 쪼개면
어느 한 계열이 구조적으로 홀대받고, 그 계열 특화 빌드가 손해를 본다. 6종(계열당 2)은
대칭이고, 게이트를 계열 누적 8 / 40 으로 두면 **저티어는 Lv8 부터** 열려 신세대 기체도
z/x 가 죽은 키가 되지 않는다. 고티어 40 은 캡스톤과 같은 문턱이라 "이 계열에 올인했다"는
선언이 액티브 스킬 하나로도 보상된다.

### 왜 방어 AI 는 쓰지 않는가

두 가지가 겹친다. **밸런스** — 방어측이 42종의 발동형 능력을 얻으면 위 맥락 2의 밴드가
통째로 무효가 되고 재계측·재튜닝 레인이 하나 더 생긴다. **정체성** — 액티브 스킬의 존재
이유는 *플레이어 조작이 기체마다 다르게 느껴지는 것*이다. AI 가 쿨다운마다 자동 발동하면
그건 그냥 DPS·생존 수치 상향이고, 이미 시그니처 패시브가 하는 일과 구분되지 않는다.

**예비역 소집에서는 쓴다 — 단 별도 규칙이 필요하다.** 거기서는 플레이어가 수호 기체를 직접
조종하므로 z/x 가 죽은 키가 되어서는 안 된다. 그런데 **장착 슬롯은 `skillInvest` 파생이
아니다** — 해금만 파생하고 2개 선택은 `Ship` 의 독립 저장이라, `GuardianBuild = { typeId,
equipped, skillInvest }`(`src/save/guardianLifecycle.ts`) 스냅샷에 실리지 않는다. 초안은
"동결된 `skillInvest` 를 읽으면 되므로 별도 규칙이 없다"고 적었으나 **그것은 사실이 아니었다**
(합의 검토에서 Architect·Critic 이 독립적으로 적발).

채택: **퇴역 시점의 장착 2개를 박제로 보존한다.** `GuardianBuild` 에 슬롯 2칸을 추가하고
`SAVE_VERSION` 8 마이그레이션이 기존 guardian 레코드까지 정규화한다. 잠긴 장비가 그대로
보존되는 것과 같은 결이며(ADR-0024), 수호 기체는 "성장이 동결된 실물 보존체"라는 정의에
장착 상태까지 포함된다. 소집 시점에 다시 고르게 하는 안은 동결 원칙과 어긋나 기각했다.

### 왜 42종이 서로 다를 수 있는가

효과 범위를 3결로 좁혔으므로 변주 축은 사거리·각도·탄수·지속·배율뿐이고, 그대로 두면
"브루저의 전방 산탄"과 "스트라이커의 전방 산탄"이 수치만 다른 물건이 된다. 게다가 기체
정체성은 이미 **시그니처 패시브 7종**이 담당하고 있어, 액티브가 그것을 반복하면 새 축이
아니라 장식이 된다.

따라서 **저작 규칙을 건다** — 기체의 6종은 그 기체의 시그니처 패시브를 *능동적으로 건드려야
한다*. 브루저는 장갑 스택을 즉시 충전하거나 소모하고, 팬텀은 은신 조건을 임의로 만들거나
끊는 식이다. 시그니처가 7종 전부 다르므로 기체 간 중복이 구조적으로 막힌다.

**스트라이커는 시그니처가 없다**(`signatureBit: -1`, 설계서 채택안 A 의 바이트 불변 조치).
비트를 새로 주면 그 결정이 무효가 되고 골든이 깨지므로, 대신 **"무색함"을 정체성으로 삼는다**
— 가장 순수한 교과서형 6종(정직한 광선·대시 강화·짧은 무적)으로 신규 플레이어의 학습
기준선이 되게 한다. 시그니처 부재가 결함이 아니라 설계가 된다.

### 왜 조준각이 아니라 이동 방향인가

자동공격은 이미 마우스 조준각을 쓴다. 액티브까지 마우스에 묶으면 **모든 의사결정이 마우스
한 축에 몰리고**, 키보드는 회피 전담이 된다. 발동 방향을 이동 입력에 묶으면 "어디로
움직이면서 쏘는가"가 판단 대상이 되어 조작의 표현력이 실제로 늘고, 뒤로 빠지며 견제하는
용법이 성립한다.

**정지 중 폴백은 조준각이다 — 대시와 같은 규칙**(`world.ts` 의 대시가 이미 이동 입력 우선,
없으면 `player.angle` 로 떨어진다). 처음에는 "마지막 이동 방향"을 검토했으나 두 문제가
있었다: ① 같은 화면에서 Space 와 z/x 의 폴백 규칙이 갈라져 조작 규칙이 두 개가 된다.
② `Entity` 에 방향 상태가 아예 없어(대시조차 저장하지 않는다) 신규 정수 필드 + 조건부
해시 폴드 + `ENTITY_HASH_LAYOUT`·`tests/invasionHash.test.ts` 동시 수정이 필요하다.
얻는 것(정지 상태 한정의 마우스 비의존)에 비해 값이 비싸고 일관성을 해쳤다. 이동 중에는
여전히 이동 입력 방향이므로 원 의도의 대부분은 보존된다.

## 귀결

**결정론·서버**

- `InputFrame.special` 의 미사용 비트 2개를 액티브 슬롯 1·2 발동에 배정한다. 파워업(0~2)·
  조우(3+) 뒤에 append 하며, 컨트롤러의 "파워업 픽 대기 중엔 조우를 소비하지 않는다" 규율과
  같은 방식으로 우선순위를 명시한다.
- 신규 `WorldState` 상태는 **정수 4개** — 슬롯별 쿨다운 2개 + 슬롯별 **버프 잔여 틱 2개**.
  방향은 조준각 폴백을 택해 필드가 없다. 초안은 "쿨다운 2개뿐"이라 적었으나 **`kind='buff'`
  가 지속 시간을 요구하므로 그것만으로는 3결을 담을 수 없다**(합의 검토에서 Architect 적발).
  `aux0/aux1` 재사용은 불가하다 — 그 두 칸은 기체별 시그니처 런타임 상태가 이미 점유했다
  (`src/sim/world.ts` 의 인코딩 표: 브루저 장갑 스택, 팬텀 무피격 틱, 버블 막 내구 등).
- 넷을 `hashWorld` **맨 꼬리 하나의 조건부 폴드**로 묶는다 — 넷이 전부 0이면 한 폴드도
  실행하지 않으므로 액티브 스킬을 안 쓴 기존 런은 **바이트 불변**이다. 장착 슬롯 id 2개는
  **별도의 조건부 꼬리**로 접는다(장착이 `powerupRng` 소비를 바꾸므로, `skillInvest` 를
  잉여인 줄 알면서 접은 것과 같은 이유).
- **42종 핸들러가 묶이는 실제 계약은 `src/sim/world.ts` 의 `aux0/aux1` 인코딩 표다.**
  시그니처 상수·순수 함수가 있는 `src/sim/shipSignature.ts` 는 상태를 갖지 않는다. 핸들러
  시그니처를 `(state, player, def) => void` 로 두면 `world.ts` 를 건드리지 않고 그 칸을
  읽고 쓸 수 있고, `aux0/aux1` 은 이미 `ENTITY_HASH_LAYOUT` 에 있으므로 **추가 폴드가 없다**.
- 그럼에도 **`verify-invasion` EF 재배포와 deno fixtures 재생성은 필수**다. 입력 wire 가
  바뀌었고, 액티브를 쓴 침공 리플레이는 새 코드로만 재현된다.
- PvE 는 리플레이를 제출하지 않으므로(ADR-0026) 서버 영향이 없다.

- **프리즈 중 입력은 버린다.** `controller.sample()` 은 파워업 픽이 대기 중이면 다른
  `special` 을 통째로 버리고, `stepWorld` 는 `pendingLevelUp`·detour 분기에서 조기 return
  한다. 액티브 비트를 그 우선순위 **아래**에 두어 기존 규율을 그대로 잇는다 — 큐잉하면
  오버레이가 닫히는 순간 원치 않은 스킬이 나가 쿨다운을 낭비한다.
- **오토파일럿이 액티브를 쓴다**(`src/sim/autopilot.ts` 한 곳). 그러지 않으면 `ff()` 벤치·
  회귀 런이 액티브 스킬을 한 번도 밟지 않아 완료 게이트 ①이 성립하지 않는다. 봇의 순수·
  결정론 규율은 유지한다(쿨다운은 `WorldState`/`Entity` 에서 읽고 내부 정적 변수 금지).
  부수 귀결로 `rosterBench` 기체 비교 기준선이 이동하므로, 이 변경 전후의 벤치 수치를
  직접 비교해서는 안 된다.

**완료 게이트 (3중, 하나라도 빠지면 미완)**

1. 하네스 화면에서 **42종 전부 발동 확인** — 이 저장소의 반복 결함("단위 테스트 그린인데
   배선이 통째로 없다" 8건)은 화면 확인으로만 잡힌다
2. **액티브 미사용 런의 골든 해시 바이트 불변** — 조건부 폴드가 실제로 중립인지의 물증
3. **액티브를 쓴 침공 리플레이가 재배포된 EF 에서 검증 통과**

**세이브**

- `Ship` 에 장착 슬롯 2칸(액티브 스킬 id 배열)을 더한다. `skillInvest` 는 그대로다 —
  해금도 성능도 전부 거기서 **파생**하므로 추가 저장이 없다.
- 재화가 아니므로 서버 원장(ADR-0027)과 무관하고, 클라 `profiles.save` jsonb 로 충분하다.

**키 재배치**
