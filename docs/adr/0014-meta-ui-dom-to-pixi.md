# 메타 UI 는 DOM 오버레이가 아니라 Pixi 캔버스로 그린다 (카툰나무풍 이관)

격납고 파일럿(2026-07-19)에서 "카툰나무풍" UI 세트를 도입하면서, 메타 화면(런 밖 화면 — 기지 맵·격납고·연구소·정제소·성계 지도 …)을 무엇으로 그릴지 결정해야 했다. 기존 구현은 전부 `document.createElement` + 인라인 `<style>` 의 **DOM 오버레이**였다. 결정: **메타 화면을 1920×1080 디자인 스페이스의 Pixi 캔버스로 이관하고, 공용 부품을 `src/ui/pixi/` 에 모은다.** 파일럿 이후 기지 맵(#1)·연구소(#2)·정제소(#3)·성계 지도(#4)까지 네 화면을 같은 방식으로 옮기며 골격이 두 종류(패널+그리드/행, 카드형)로 늘어난 지금 결정을 굳힌다.

이유는 자산 때문이다. 이 세트의 나무 프레임·버튼·슬롯은 9-slice 픽셀아트이고 `scaleMode='nearest'` 로 그려야 의도한 모습이 나온다. DOM 에서 같은 결과를 내려면 `border-image` 와 `image-rendering: pixelated`, 그리고 레터박스 스케일(`fitToWindow`)을 CSS 로 다시 구현해야 한다 — 게임 캔버스는 이미 그 스케일을 하고 있으므로 **같은 규칙을 두 곳에서 관리**하게 된다. 창 크기·DPR 이 바뀔 때 두 좌표계가 어긋나면 "UI 만 크기가 다른" 증상이 되고, 실제로 파일럿에서 dpr>1 레터박스 결함으로 한 번 드러났다. 대안(DOM 에 세트를 CSS 로 재현)은 초기 비용은 싸지만 이 이중 관리를 영구히 떠안는다.

## 결정 사항

- **레이어 분리.** `src/ui/pixi/**` 는 순수 render/UI 다. sim(`src/sim/**`)은 이 디렉터리를 모르고, UI 는 sim 상수(숫자)와 `Profile` 만 읽는다. 리롤 시드처럼 무작위가 필요한 곳은 UI 레이어 안에서 `Math.random()` 을 써도 된다 — 결정론 계약(ADR-0005)은 sim 안에서만 성립하면 되고, UI 는 리플레이 해시에 들어가지 않는다.
- **DOM 클래스 존치.** 이관된 화면의 DOM 클래스(`src/ui/planetSelect.ts` 등)는 **삭제하지 않는다**. 공개 인터페이스(`show`/`hide`/`visible`)와 콜백·선택 타입(`LaunchSelection` 등)을 Pixi 판이 그대로 따르게 해서 `main.ts` 는 생성자 한 줄만 바꾼다. 회귀가 나오면 그 한 줄을 되돌리는 것이 롤백이다. **제거 조건**: 롤아웃 대상 8화면이 전부 이관되고 사용자 플레이 판정을 통과한 뒤, 한 마일스톤 동안 롤백 없이 지나가면 미참조 DOM 클래스를 일괄 삭제한다. **8화면 이관은 2026-07-20 완료**(설정 #8 + 함께 옮긴 타이틀) — 남은 것은 관찰 기간뿐이고, 삭제 대상 목록은 `.omc/plans/cartoonwood-rollout.md` "다음 단계" 절에 적어 뒀다. 방어 사령부는 아직 DOM 이므로 삭제 대상이 아니다. 타입(`LaunchSelection` 등)은 그 뒤에도 DOM 파일이 아닌 적절한 위치로 옮겨 남긴다. **예외 한 건**: 카드 관리(#7)는 독립 DOM 화면이 아니라 방어 사령부 오버레이 **안의 섹션**이었다 — 존치하면 같은 기능이 두 곳에 뜨므로 보관함·상점·합성 블록은 걷어내고 장착 슬롯 요약만 남겼다(사용자 판정). 화면 단위 롤백이 성립하지 않는 유일한 경우이고, 되돌림은 그 커밋의 revert 다.
- **공용 부품 경계.** `src/ui/pixi/` 에 올리는 것은 **둘 이상의 화면이 실제로 쓰는 것**뿐이다(`nineSlicePanel`·`button`·`slotGrid`·`tooltip`·`titleBar`·`card`·`text`·`theme`·`uiTextures`). 한 화면에서만 쓰는 조립(성계 지도의 티어 선택 행, 정제소의 어픽스 행)은 그 화면의 private 메서드로 둔다. 두 번째 소비자가 생기는 시점에 승격한다 — 승격은 값이 조용히 갈리는 것을 막는 조치지, 미리 해두는 일반화가 아니다.
- **여백은 코드로 강제한다.** 콘텐츠는 `panelContent(w, h)` 가 주는 상자(프레임 46 + 여백 14 = 60px) 안에만 놓는다. 화면마다 프레임 오프셋을 재유도하지 않는다 — "테두리를 침범하지는 않는데 딱 붙어서 얹혀 보인다"는 결함을 사용자가 **두 번** 지적했고, `border` 만 피하는 계산으로는 구조적으로 막을 수 없었기 때문이다. 유일한 예외는 잠금 딤처럼 안쪽 전체를 덮는 오버레이이고, 이것도 `panelDim()` 이라는 이름으로 코드에 박아 뒀다.
- **검증 절차.** 완료 선언 전에 ① 1920×1080 스크린샷 ② **패널 모서리 확대 크롭**(전체 스크린샷으로는 붙은 콘텐츠를 놓친다) ③ 사용자 실화면 승인을 모두 거친다. 타입체크·린트·테스트 통과는 시각 검증을 대체하지 않는다.

## Consequences

- 메타 화면과 게임 화면이 스케일·DPR 규칙을 하나만 공유한다 — 레터박스 결함이 한 곳에서만 고쳐진다
- UI 킷 자산이 바뀌면 `src/ui/pixi/` 부품 한 곳만 고치면 모든 메타 화면이 함께 따라온다
- 캔버스 화면은 DOM 오버레이와 달리 **다음 화면이 자동으로 덮어주지 않는다** — 화면 전환마다 `clearToMenu()` 에서 명시적으로 `hide()` 해야 한다(실제 결함 사례). 새 캔버스 화면을 추가하면 반드시 여기에 등록한다
- 캔버스 화면은 DOM HUD(`#pb-hud`)를 가리지 못한다 — show 에서 숨기고 hide 에서 복원한다
- **캔버스로 옮긴 UI 는 남아 있는 DOM 오버레이 아래로 내려간다.** 캔버스는 DOM 요소 하나이므로 z-index 로 뒤집을 수 없다. 설정(#8)은 DOM 시절 `z-index:60` 으로 모든 오버레이 위였는데 캔버스로 들어가면서 그 특권을 잃었다 — 불투명 배경의 DOM 화면(타이틀)이 톱니를 통째로 덮어, **그 화면도 함께 이관하는 것이 유일한 해법**이었다. 모든 화면 위에 떠야 하는 크롬 UI 를 옮길 때는 "아직 DOM 인 화면"을 먼저 셈한다. 남은 예외는 방어 사령부(이관 예정)와 인런 파워업·스티커 모달(즉시 결정 모달이라 수용)
- **모든 화면 위에 떠야 하는 크롬 UI 는 렌더 루프에서 stage 맨 앞으로 되돌린다.** 화면들이 `show()` 에서 자기를 맨 앞으로 올리므로 한 번 올려 두는 것으로는 안 된다. `raise()` 는 이미 마지막이면 no-op 이라 매 프레임 불러도 싸고, 새 화면을 추가할 때 등록을 잊을 곳이 없다
- **상호작용은 생성자에서 한 번만 건다.** 텍스처 로드 후 다시 부르는 build 함수 안에 리스너를 두면 재등록되어 클릭 한 번에 핸들러가 두 번 돈다(설정 톱니가 열렸다 즉시 닫힌 실측 결함). build 함수는 시각 요소만 다시 만든다
- i18n 카탈로그는 DOM 판과 공유하므로 **컬러 이모지가 캔버스에서 흑백 두부 글리프**로 떨어진다. 카탈로그는 건드리지 않고 라벨에서만 `stripEmoji()` 로 걷어낸다(▶ ◀ 같은 기하 기호는 보존)
- 접근성·텍스트 선택·브라우저 확대 같은 DOM 기본 기능을 잃는다. 게임 UI 라 수용하되, 텍스트 선명도는 모든 `Text` 에 `resolution: 2` 로 보완한다
- **9-slice `border` 는 나무 살의 두께가 아니다.** `ui_panel.png` 의 살은 37~39px 에서 끝나고 테두리 46 은 늘어나는 중앙 슬라이스가 살을 물지 않게 잡은 여유값이다. 코드로 까는 어두운 채움의 inset 을 `border` 에서 유도했더니(`border - 2`) 채움과 살 사이에 6px 짜리 투명 링이 남았다 — 평면 배경 위에서는 배경색이 비쳐 안 보이고, **화면 위에 얹는 팝업에서만** 뒤 화면이 비치는 띠로 드러난다(설정·타이틀·연구소 스킬 목록). 프레임 밑에 깔리는 값은 자산 실측에서 오지 추정에서 오면 안 되고, 이런 상수는 자산이 다시 뽑힐 때 조용히 어긋나므로 `tests/panelFrameGeometry.test.ts` 가 PNG 알파를 직접 읽어 고정한다
- UI 는 자동 테스트로 잡히지 않는다 — 신규 단위 테스트는 `gridPositions` 처럼 UI 독립 레이아웃 헬퍼에만 붙이고, 나머지는 위 검증 절차(스크린샷 + 확대 크롭 + 사용자 판정)로 지킨다
