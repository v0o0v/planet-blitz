# 강제 스크롤 정책 축 — ANCHOR / WORLD 구분

강제 스크롤 모드는 세 갈래다 — 블록격파(−Y 종스크롤)·레이싱(+X 횡스크롤)·침공 3레이어(L1 −Y / L2 +X / L3 고정). 지금까지 이 모드들에서 **모든 엔티티는 월드 절대 좌표**였고, 창(scroll window)이 엔티티에 미치는 영향은 세 가지뿐이었다: 플레이어 클램프(`clampToWindow`), 적 컬링(`cullScrollEnemies`), 스폰 기준점(`BLOCKBREAK_SPAWN_AHEAD`/`RACING_SPAWN_AHEAD`). 즉 **강제 스크롤되는 엔티티는 하나도 없었다** — 창만 움직이고 월드는 가만히 있었다.

여기서 모드를 성립 불가로 만드는 결함이 나왔다. `DEFAULT_CONFIG.playerSpeed = 720 u/s = 12 u/tick` 과 `INVASION_SCROLL_SPEED = 12` 가 **정확히 같다**. 따라서 플레이어의 전방 상대속도 최댓값이 **0**이다. `clampToWindow` 가 한 번 창 뒤 경계에 붙여 놓으면 그 뒤로는 전력 전진해도 영원히 뒤 경계에 붙어 있고, 회피 기동으로 잃은 전방 거리는 회복 수단이 없다. 가속 구간(`INVASION_ACCEL_MAX_CP = 200`)에서는 창이 24 u/tick 으로 2배 빠르니 상대속도가 음수로 확정된다. 유일한 만회 수단인 대시(`dashSpeed 2800` × 1틱 ≈ +46.7u, 쿨 42틱 ≈ 평균 +67 u/s)로 창 반폭 960 을 복귀하려면 약 14초가 걸린다. `invasion/scroll.ts` 헤더는 이 속도 일치를 "전진하지 않으면 창 뒤편에 밀린다"는 **의도**로 적어 두었으나, 실제 귀결은 "한 번 밀리면 되돌릴 수 없다"였다.

결정: **엔티티별로 "창에 앵커되는가(ANCHOR) / 월드에 남는가(WORLD)"를 가르는 정책 축을 순수 술어로 도입하고, 플레이어는 부분 앵커(70%)한다.**

- 술어는 `src/sim/scrollMode.ts` 의 `scrollAnchored(e: Entity): boolean` 다. **신규 `Entity` 필드 0 · 신규 `WorldState` 필드 0 · 신규 해시 폴드 0**. 이 리포의 관례(`isBreakableWall`·`isActiveTurret`·`isBoostPad`·`isGimmick`)와 동형이다.
- 정책 표:
  - `ANCHOR 70% + CLAMP`: `player`
  - `ANCHOR 100%`: `gem` `loot` `supply` `echo` `encounterPortal`(봉인 포함) `encounterAltar` `turretPickup`(`phase === 1` 활성 포탑만)
  - `WORLD`(현행 유지): 적·보스·탄 2종·`wall`·`boostPad`·`hazard`·`destructible`(오염 노드·반격 장치)·`core`·`decoyCore`·`guardian`·`shelter`·침공 8종·미활성 `turretPickup`
- `turretPickup` 이 **kind 하나에 정책 둘인 유일한 케이스**다(`phase` 로 갈린다). 순수 테이블(`Record<EntityKind, Policy>`)로는 이 예외를 담을 수 없어 술어가 필요했다.
- **창 안에 있을 때만 앵커**한다(`insideScrollWindow`). 적은 전방 700u, cluster 포메이션은 최대 ~2400u 밖에 스폰되므로, 창 밖 드랍을 무조건 앵커하면 상대 위치가 얼어붙어 영영 도달 불가가 된다.
- **플레이어는 100% 가 아니라 70%** 다. 100% 앵커면 뒤로 밀리는 일이 아예 없어져 `racingRearPressure`(레이싱의 유일한 실패 압박)가 사실상 사재된다. 70%면 정지 시 −4 u/tick(조금씩 밀림)·전방 전력 시 +8(확실한 만회)·가속 200cp 전방 전력 시 +4 가 되어 페이스메이커 긴장과 만회 가능성이 동시에 성립한다. (설계 시 계산한 −3.6/+8.4/+4.8 은 trunc 전 이론값이고, `Math.trunc` 를 거친 **실측값이 위 정수**다 — `tests/scrollAnchorWiring.test.ts` 가 전진 +8 을 23틱, 정지 −4 를 57틱 연속으로 못박는다.) 계수는 `PLAYER_ANCHOR_PERCENT = 70`, TODO(밸런스).
- **적용 범위는 PvE 스크롤 모드 + 침공 3레이어 모두**다. 같은 결함이 두 곳에 있으므로 일관 해소한다. 창이 없는 모드(뱀서류·수축·추격·오염)는 코드 경로 자체를 타지 않는다.
- 적용 순서는 `창 전진` → `앵커 가산 루프(플레이어 포함)` → `stepPlayer(입력 이동 → 벽 슬라이드 → 창 클램프)` 다. 앵커가 벽 슬라이드보다 앞이라 플레이어가 벽에 박힌 상태로 남지 않고, 블록격파에서 벽에 막히면 `isPinnedByWall` 압사가 정상 발동한다. **압박의 원천이 "속도 열세"에서 "장애물"로 이동하는 것이 이 설계의 핵심 의도**다.
- 앵커 델타는 `scrollStep(accelCp)` 재계산이 아니라 **전진 전/후 오프셋의 차**로 산출한다 — 전진 함수가 같은 호출에서 `accelCp` 를 갱신하므로 재계산은 어긋난다. 두 오프셋이 정수 누적이라 차이도 정수다.

## Considered Options

- **플레이어 속도만 상향**(`playerSpeed` 720→900, 구조 무변경) — 변경량이 가장 작지만 가속 200cp(24 u/tick) 구간에서는 여전히 밀려 결함이 그대로 남아 기각.
- **엔티티 플래그 필드 추가**(`e.anchored`) — 런타임 개별 예외가 가능해 표현력은 가장 높으나 `hashEntity` 조건부 폴드가 필요하고 스폰 지점이 수십 곳이라 누락 위험이 커서 기각.
- **kind 상수 테이블 + `ownerId` 마커 예외** — `turretPickup` 의 `phase` 같은 비-`ownerId` 예외를 담지 못해 결국 술어가 필요하다. 게다가 `ownerId` 는 냉기 감속 틱 등으로 이미 다중 용도라 여유가 없다(ADR-0033 구현 때 확인된 함정).
- **드랍은 앵커 대신 "창 뒤 경계 통과 시 자동 회수"** — 연산·해시 영향은 더 작으나, 화면에 남아 있는 것과 사라지는 것의 시각적 구분이 생기지 않아 이 ADR 의 목적(무엇이 강제 스크롤되는지 플레이어가 알 수 있게 한다)에 미달해 기각.
- **플레이어 100% 앵커 + 레이싱 실패 조건 신설**(구간 제한시간·연료 등) — 압박을 다른 축으로 옮기는 정공법이지만 범위가 크게 늘어나 기각.

## Consequences

- 앵커된 젬은 화면을 벗어나지 않아 **수집 난이도가 크게 내려간다** → 스크롤 모드 xp 획득률이 상승한다. 출시 전 밸런스 패스 항목이다.
- `racingRearPressure` 발동 빈도가 줄어 실패 압박이 약해진다 → 계수 재측정이 밸런스 패스 항목이다.
- **순전진량은 가속에 반비례한다**: 순전진 = `12 − Math.trunc(0.3 × 창델타)`. 기준 가속(창 12)에서 +8/tick, 창 14 에서 +7, 최대 가속 200cp(창 24)에서 **+4** 가 된다. 즉 구간을 전멸시켜 가속을 벌었을 때 만회가 **가장 불리**해진다. 결함은 아니다 — 최대 가속에서도 양수라 만회 가능성은 전 구간 성립한다. 다만 "전멸 보너스가 만회를 방해한다"는 역결합이므로 밸런스 패스에서 볼 값이다.
- **벽에 완전히 막히면 창 대비 −12/tick 으로 후퇴한다**(정지 시 −4 의 3배). 앵커 가산 +8 이 `slideCircleWalls` 로 원위치로 되돌려지기 때문이다. "압박이 속도 열세에서 장애물로 이동한다"는 이 ADR 의 의도와 일치하지만, 후퇴 강도가 정지 시보다 3배라는 사실은 설계 시 예상하지 못했다.
- **침공 난이도가 재분배됐다.** 플레이어 기동이 회복되자 `tests/invasionBalance.test.ts` 중위 밴드(기지 #15~#20)의 기지간 승률 편차가 **14.164 → 28.767pp** 로 벌어졌다:

  ```
  #15~#20  33.3/ 8.3/41.7/ 16.7/50.0/33.3  (변경 전, 평균 30.6%)
        →  33.3/25.0/66.7/100.0/16.7/33.3  (변경 후, 평균 45.8%)
  ```

  주범은 단순 분산 확대가 아니라 **양방향 이동**이다 — #18 이 16.7 → 100.0(+83.3pp), #19 가 50.0 → 16.7(−33.3pp) 로 밴드가 위아래로 찢어졌다.
- **인과: 이전 난이도의 일부가 이동 결함에서 나왔다.** 플레이어가 창 뒤 경계에 눌려 있으면 뒤로의 회피 공간이 0 이고 L2 설비 회랑에서 방어포를 피할 여지가 없었다. 앵커로 기동을 회복하니 생존이 쉬워졌다. **적측 앵커 정책 누락은 아니다** — `src/sim/invasion/formation.ts` 는 편대를 창 중심(`runtime.scrollX/scrollY` + AHEAD 오프셋) 기준으로 스폰하고 플레이어 좌표에 의존하지 않는다(파일 헤더가 계약으로 명시). #19 만 반대로 어려워진 것은 그 기지 배치가 "플레이어가 뒤에 있음"을 전제로 짜였을 가능성이 크다.
- 다른 밴드는 신호가 반대다 — **하위 밴드는 전 기지 100% 로 포화**(편차 3.765 → 0.000), **중하 밴드는 오히려 개선**(30.211 → 28.071pp). 시간초과 실패는 세 밴드 모두 0 건이라 배선 결함이 아니다.
- 위에 따라 스모크 허용치를 **중위 28 → 29** 로만 넓혔다. 근거는 실측 28.767 기준 **최소값**이며, 기지 재배치는 출시 전 밸런스 패스로 넘긴다(프로젝트 방침 defer-balance-tuning). 다른 밴드 허용치는 건드리지 않았다.
- 밸런스 큐(출시 전 일괄, 지금 손대지 않음 — 프로젝트 방침): ① `PLAYER_ANCHOR_PERCENT` 튜닝 ② `RACING_PRESSURE_DAMAGE`·`RACING_REAR_PRESSURE_MARGIN` 재측정 ③ 스크롤 모드 젬 가치·자석 반경 조정 ④ 가속 구간의 순전진량 감소(위 항목) 완화 여부 ⑤ **침공 기지 #18(승률 100% = 사실상 무저항)·#19 재배치** — 중위 밴드 편차의 주범이고, 재배치 후 중위 허용치를 28 로 되돌리는 것이 목표다.

### 해시 계약 영향 (ADR-0005)

- 가산량은 `Math.trunc(delta × pct / 100)` 로만 구한다. 정수 × 정수 / 100 에 IEEE-754 단일 나눗셈 + `Math.trunc` 뿐이라 Node(클라)·Deno(서버) 비트 동일이며, `invasion/scroll.ts` 의 centi-percent 규율과 동형이다.
- 대가는 계수 해상도다 — 70% 에서 12→8(실효 66.7%), 24→16 이 된다.
- RNG·`Date.now`·전역을 쓰지 않는다. 창이 없는 모드는 호출 자체가 없어 골든이 바이트 불변이다.
- 침공 per-tick 해시는 틱 0부터 갈린다(틱 0 에 이미 창이 전진하고 앵커가 돈다) → `tests/fixtures/encounter-baseline.json` 의 침공 항목 재생성이 필요하다. **같은 파일의 PvE 항목(카르곤=뱀서류·베르단=수축)은 바이트 불변이어야 하며, 그것이 창 게이트가 새지 않았다는 물증이다.**
- `scripts/deno-verify/fixtures.json` 은 **재생성이 불필요하다** — 12 시나리오가 침공 경로를 태우지 않아 앵커 도입 후에도 커밋된 픽스처와 일치했다(Node 2회 bit-identical 확인).
- **`verify-invasion` Edge Function 재배포는 필수다.** 픽스처와 무관한 이유다 — EF 는 서버에서 침공 리플레이를 **번들된 sim 소스로 재계산**하므로, sim 이 바뀐 채 EF 를 방치하면 서버는 옛 sim 으로 계산해 **모든 침공이 해시 불일치로 거부**된다. 배포 후 번들 소스 커밋이 최종 HEAD 인지 반드시 대조한다(M8 1회차 배포가 이 대조를 빼먹어 무효였다). 리플레이 TTL 이 48h(ADR-0027 계열 치팅 방어)라 기존 저장 리플레이 무효화 피해는 제한적이다.
- `tests/invasionHash.test.ts` 는 관계 단언(`not.toBe`·`toEqual(a,b)`)만 쓰므로 구조적으로 깨지지 않는다.
- `tests/invasionE2E.test.ts` 의 증인 시드를 재선정했다 — `WINNING_SEED_FILLED` 를 **10 → 9** 로 바꿨다(`fix/weapon-range-semantics` 의 `7 → 10` 에 이은 두 번째 재선정). 그 파일 주석이 "sim 이 바뀌면 증인 시드도 다시 골라야 한다"를 정본으로 못 박고 있으므로 단언 약화가 아니라 시드 교체가 정규 대응이다. 시드 1~120 탐색에서 전 단언을 만족한 것은 1·9·21 이었고, 최소값 1 은 `WINNING_SEED_EMPTY` 와 값이 겹쳐 두 상수가 뒤바뀌는 회귀를 못 잡게 되므로 9 를 골랐다.

## 개정 2026-07-27 — WORLD 축을 "지형·구조물" 로 다시 정의한다

**바뀐 것:** `scrollAnchored` 의 축 분류를 뒤집었다. 이전에는 **ANCHOR 가 소수**(플레이어·회수물 5종·활성 포탑)였고 나머지 전부가 WORLD 였다. 이제 **WORLD 가 소수**다 — 월드에 깔린 지형·구조물(`wall`·`destructible`·`hazard`·`magnetEmitter`·`bombDevice`·미활성 `turretPickup`·`boostPad`·`shelter`·`core`·`decoyCore`·침공 설비 4종)만 창이 흘려보내고, **살아 움직이는 실체는 전부 ANCHOR**(플레이어·적·보스·탄 2종·편대·드론·수호기·회수물·활성 포탑)다.

**왜:** 사용자 지시(2026-07-27) — "강제 스크롤 되는 곳에서는 벽 빼고는 다 강제 스크롤 안되게". 교전 중이던 적 무리와 쏘아 놓은 탄이 플레이어 의지와 무관하게 창 뒤로 흘러가 `cullScrollEnemies` 에 정리되는 것이 문제였다. 압박은 **지형 통과와 시간**에서 와야 하고 전투 상대가 스스로 사라져서는 안 된다.

**"벽만" 을 문자 그대로 적용하지 않은 이유(실측):**
- 청크 기믹(파괴체·영구 지형 해저드·자석·폭탄·미활성 포탑 픽업)의 **컬링은 엔티티 위치에서 청크를 역산**한다(`world.ts` `activateChunks`). 이것들이 창을 따라오면 영영 컬 반경 밖으로 나가지 않아 `MAX_ACTIVE_GIMMICKS`(48)가 포화되고 **새 청크 생성이 지연돼 지형이 더 이상 나오지 않는다**. 블록격파 실측에서 첫 벽 도달이 120틱 → 175틱 이후로 밀렸다.
- 침공 설비·코어(기지 구조물), 레이싱 부스트 패드, 추격 대피소는 **통과해야 하는 코스**다. 앵커하면 기지가 플레이어를 쫓아다니고 부스트 패드가 영구 가속이 된다.
- 해저드는 지형이든 적이 깐 장판이든 **월드 좌표에 깔리는 것**이다. 앵커하면 장판이 따라다녀 회피가 성립하지 않는다.
