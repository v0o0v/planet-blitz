# ADR-0042 — 촉매 상점: 촉매 잔재로 닫은 자기 완결 경제

- 상태: 채택 (2026-07-31)
- 관련: ADR-0029(촉매 시스템 — 변칙 경보 대체) · ADR-0027(재화 서버 원장) ·
  ADR-0026(PvE 3중 캡) · ADR-0022(행성 차별화 — 특산의 행성 귀속)

## 맥락

촉매는 PvE 드랍으로만 얻는다. 이 설계는 `.omc/specs/deep-interview-catalyst-system.md`
에서 의도적으로 좁게 잡은 것이고, 거기에는 *"촉매 상점·합성 — 획득은 PvE 드랍 주축"* 이라고
상점이 **명시적 제외 항목**으로 적혀 있다.

운영해 보니 드랍 운의 분산이 그대로 노출된다. 파워축·보스 특산은 `dropWeight` 가 낮아 드물고,
반대로 안 쓰는 촉매는 계속 쌓인다. 플레이어에게 남는 조정 수단은 **분해**(촉매 → 크레딧) 하나뿐인데,
이건 촉매를 버리는 행위지 원하는 촉매에 가까워지는 행위가 아니다. 쌓인 재고를 원하는 종류로
바꿀 창구가 없다.

가장 쉬운 해법은 "크레딧으로 촉매를 판다"이지만, 이건 CONTEXT 의 계약
*"촉매 = 파밍이 다음 파밍을 키우는 닫힌 원환"* 을 깬다. 촉매에는 자원 보상축(`resource`)이 있어서,
크레딧으로 촉매를 살 수 있으면 **크레딧 → 자원축 촉매 → 자원 → 더 많은 크레딧** 의 자기 증식 고리가
생긴다. 3중 캡(ADR-0026)이 상한을 씌우긴 하지만, 캡이 방어선이라는 것 자체가 설계가 인플레
방향으로 기울었다는 뜻이다.

## 결정

**촉매 상점을 만들되, 촉매 전용 재화인 `촉매 잔재`로만 결제하게 해 경제를 촉매 안에 닫는다.**

1. **촉매 잔재** 신설 — 획득처는 촉매 **분해** 하나, 사용처는 촉매 상점 구매 하나.
2. **분해 보상 전환** — 촉매 분해는 이제 크레딧을 주지 않고 촉매 잔재만 준다.
   (장비 분해는 종전대로 크레딧·광물.)
3. **가격은 희소도 한 축에서 파생** — `구매가 = K / dropWeight`,
   `분해 환급 = r × 구매가`, 시작값 `r = 0.5`. 계수는 전부 `// BALANCE`.
4. **공용 30종만 판매** — 특산 촉매는 진열하지 않는다. 분해는 되지만 되살 수 없어
   특산 → 공용은 되돌릴 수 없는 일방 흐름이다.
5. **상시 전 카탈로그·해금 없음** — 로테이션 재고를 두지 않는다.
6. **구매 전용** — 상점에 파는 방향은 없다. 촉매를 재화로 바꾸는 행위는 종전대로 **분해**다.
7. **위치는 촉매 보관함 안의 탭** — 기지 시설을 늘리지 않는다(모듈 경제가 방어 사령부 안에
   사는 것과 같은 선례).

## 계약 세부

- **가격 정본은 TS, 서버에는 최종 정수 하나만 미러.** `catalyst_defs` 에 `buy_price` 정수
  컬럼을 더해 **48종 전부** 시드한다(특산도 가격을 갖는다 — 살 수 없는 정가표로만 존재하며
  환급액 산정 근거가 된다). 서버는 환급을 `floor(buy_price × r)` 로 계산한다. 산식을 SQL 에
  중복 구현하지 않으므로 반올림 차이로 클라 표시가와 서버 청구액이 어긋날 여지가 없다.
  `catalyst_defs` 는 상단에 동기화 의무 배너가 붙은 **수동 미러**라 `dropWeight`·`K` 튜닝이
  조용히 어긋날 수 있다. 그래서 **가격 48행 시드는 TS 카탈로그에서 생성**하고, vitest 가
  마이그레이션 파일을 읽어 TS 값과 대조한다 — 시드 갱신을 잊으면 CI 가 깨진다.
  (드리프트가 나면 화면 표시가와 서버 청구액이 갈라져 플레이어가 다른 값에 구매하게 된다.)
- **원장은 `profiles.catalyst_residue` 컬럼**(`>= 0` 체크). `grant_currency` 와 3중 캡
  파이프는 **거치지 않는다** — 외부 유입이 0이라 캡의 관심사가 아니고, 캡 산정·이상치
  플래깅 쿼리에 축을 늘리지 않기 위해서다. 잔재 변동은 분해·구매 두 RPC 트랜잭션 안에서만
  일어난다(차감과 적립이 같은 트랜잭션).
- **특산 촉매도 분해된다.** 다만 상점에 없으므로 되살 수 없다.
- **분해 조작 단위는 종류별 수량 지정** — 현행 `salvage_catalyst(catalyst_id, qty)` 를
  그대로 쓰고 화면에 수량 선택만 붙인다. 여러 종류 일괄 분해는 오조작 피해가 되돌릴 수 없어
  넣지 않는다.
- **잔재 잔고는 촉매 보관함·상점 화면에서만 표시**한다. 전 화면 상단 재화 칩(크레딧·광물)에는
  올리지 않는다 — 촉매 밖에서 쓸 수 없는 재화라 다른 화면에서는 소음이다.
- **온라인 전용** — 촉매 보유 정본이 서버라는 기존 계약을 그대로 따른다.

## 근거

- **총량이 늘지 않는다.** 잔재는 촉매를 없애야만 생기고, 스프레드(`r < 1`) 때문에 교환할수록
  촉매 총량은 오히려 줄어든다. 상점이 공급하는 것은 수량이 아니라 **종류 선택권**이다.
  그래서 이 경로는 3중 캡의 개연성 검증 대상이 아니고, 새 지급 캡·새 치팅 표면이 생기지 않는다.
- **인플레 고리가 구조적으로 불가능하다.** 잔재는 촉매 밖에서 가치가 0이라, 자원축 촉매로
  번 크레딧이 다시 촉매로 돌아오는 경로 자체가 없다.
- **비율이 기대값 중립이다.** 양쪽 모두 `dropWeight` 에서 파생하므로 "흔한 N개 → 귀한 1개"가
  드랍 확률 그대로 환산된다. 비용은 오직 스프레드다.
  (정정 2026-07-31 — 초안의 *"어떤 촉매를 녹여도 손해도 이득도 없다"* 는 정수 절하를 빼고 쓴
  문장이다. `W_SIGNATURE = 8` 인 특산 일반 12종은 구매가 `12.5 → 12`, 환급 `6` 이라 드랍당 기대
  잔재가 48 로, 다른 계단의 50 보다 **4% 낮다**. 공용·파워축·ascendant 는 정확히 중립이다.
  실해는 없고 밸런스 손잡이도 그대로지만 문구를 정확히 한다.)
- **특산의 행성 귀속이 보존된다.** ADR-0022 의 종류 축 차별화는 "그 행성에 가야 얻는다"에
  기대고 있다. 특산을 팔면 톡사르를 한 번도 안 가고 톡사르 특산을 쥐게 된다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| 크레딧으로 결제 | 자원축 촉매를 통해 크레딧 → 자원 → 크레딧 자기 증식 고리가 생긴다. 3중 캡을 방어선으로 쓰게 되는 설계는 이미 기운 설계다 |
| 잔재를 런 드랍으로도 지급 | 촉매 총량이 늘어나 지급 캡·개연성 검증이 필요해지고, 촉매 드랍 자체의 의미가 희박해진다 |
| 침공·복수전 보상으로 지급 | 촉매는 "PvE 전용·침공 불개입"이 명시된 계약이다. PvP 가 PvE 파밍 파워를 공급하는 새 연결이 생긴다 |
| 분해 보상을 크레딧과 병행 | 촉매가 크레딧 파밍 수단으로 남아 salvage 축 캡 설계를 계속 져야 하고, "촉매 경제는 닫혀 있다"는 정체성이 흐려진다 |
| 분해 환급도 균일액 | 흔한↔귀한 교환이 희소도를 무시하게 돼, 파워축·보스 특산을 흔한 촉매로 양산할 수 있다 |
| 잔재 없이 촉매끼리 직접 교환(A n개 → B 1개) | 새 재화·컬럼·아이콘·가격 미러가 전부 불필요해 구현량이 절반이지만, **부분 누적**을 잃는다. 잔재는 안 쓰는 촉매를 보이는 대로 녹여 두었다가 나중에 원하는 것을 고를 수 있게 하는데, 직접 교환은 매번 "지금 n개를 내놓겠는가"를 강요해 잔동이 영영 버려진다 |
| 1시간 로테이션 재고 | 접속 동기는 생기지만, 총량이 안 늘고 가격이 이미 희소도를 반영하는 이상 재고 제한은 마찰만 남긴다. 로테이션 상점은 모듈 경제가 이미 담당한다 |
| 플레이어 간 거래소 | 계정 간 재화 이전 경로가 생겨 3중 캡(정직 파밍 속도 상한)이 무효화되고, 봇·복수 계정·현금거래 방어가 통째로 새 과제가 된다 |

## 결과

- **좋은 점**: 드랍 운 구제 창구가 생기고, 안 쓰는 촉매가 자원이 된다. 새 지급 캡·새 치팅
  표면이 0이라 서버 방어 설계가 늘지 않는다. 밸런스 손잡이가 `K`·`r` 둘뿐이다.
- **비용**: 재화가 셋으로 늘어(크레딧·광물·촉매 잔재) 원장·HUD·i18n 에 축이 하나 더
  붙는다. 촉매 분해로 들어오던 크레딧 수입이 사라져 크레딧 유입이 그만큼 준다 —
  미출시라 마이그레이션 부담은 없으나, 크레딧 밸런스 패스에서 이 항을 빼고 다시 봐야 한다.
- **부수**: `salvage_catalyst` 의 보상 경로가 바뀌므로 SQL 상수 `SALVAGE_CREDITS_PER_UNIT`
  중 촉매 몫이 사문화된다.
  (정정 2026-07-31 — 초안은 `CAP_SALVAGE_CREDITS` 도 함께 묶었으나 **틀렸다**. 장비 분해가
  `'salvage'` source 를 계속 쓰므로(`src/ui/pixi/hangar.ts:445` · `src/save/settlement.ts:334`)
  `CAP_SALVAGE_CREDITS`·`CAP_SALVAGE_MINERALS` 는 **사문화되지 않는다**. 지우면 장비 분해의
  캡이 사라진다.)
- **순 방어 감소**: 지금 촉매 축은 하류 `grant_currency` 를 타면서 `currency_grants` 원장과
  `flagged` 플래깅에 잡힌다. 이 결정 이후 그 관측에서 빠지므로, 사라지는 것은 신규 축이 아니라
  **기존 관측**이다. 이후 촉매 축의 상태는 아래 Follow-up ⓐ 와 합쳐 **"무캡 + 무원장"** 이 된다.
  (2026-07-31 해소 — Follow-up ⓐ 가 `catalyst_grants` 원장과 누적 캡·플래깅으로 셋을 되돌렸다.
  촉매 축은 이제 `currency_grants` 가 아니라 **자기 원장**에서 관측된다.)
- **되돌리기**: 잔재를 크레딧으로 되돌리려면 원장 잔량 보상 처리가 필요하다. 미출시 동안은
  싸고, 출시 후에는 비싸다.

## Follow-ups

- **ⓐ `grant_catalyst` 누적 캡 부재 — ✅ 해소(2026-07-31, `20260801000000_catalyst_grant_cap.sql`
  원격 적용 완료). 출시 게이트 해제.** 아래는 당시 기록이고, 해소 내역은 이 항목 끝의
  *해소* 절에 있다.
  클라가 호출 가능한데 상한이 per-call `CAP_GRANT_PER_CALL = 100` 하나뿐이다
  (`supabase/migrations/20260727000000_catalyst_ledger.sql:172`). 횟수 제한이 없으므로 반복
  호출로 촉매를 무제한 적립할 수 있다.
  **클라 배선은 실재한다(2026-07-31 전수 확인).** 계획 단계에서는 "`src/net/` 에 래퍼가 안
  보여 위험 창이 아직 안 열렸을 가능성"으로 적혀 있었으나, 실제로는 `src/net/gateway.ts:154`
  의 `grantCatalyst` → `src/net/index.ts:417` 의 `grantCatalystDrops` → `src/main.ts:1486`
  정산 경로로 **이미 연결돼 있다**. 즉 위험 창은 열려 있다.
  이 결정이 촉매 축의 하류 관측(원장·플래깅)을 제거하므로 방어가 순감한다 — 관측을 스스로
  지운 결정이 복구 시점을 안 정하면 영영 안 돌아온다. **주체 = 보안 레인.**

  **해소 (2026-07-31 — `supabase/migrations/20260801000000_catalyst_grant_cap.sql`)**

  재화 축(ADR-0026/0027)이 이미 검증한 형상 — **누적 캡 + 원장 + 플래깅** — 을 촉매 적립 축에
  그대로 이식했다. 세 결손을 하나씩 되돌린다.

  | 결손 | 복구 |
  |---|---|
  | 무캡 | `grant_catalyst` 에 1h 360 / 24h 2160 누적 캡. 초과분은 **예외가 아니라 클램프** — 정산 경로가 fire-and-forget(`grantCatalystDrops`)이라 예외를 던지면 정직한 플레이어가 캡 근처에서 드랍을 통째로 잃는다 |
  | 무원장 | `catalyst_grants`(본인 select 만·쓰기 정책 부재·TTL 48h GC). 누적 캡의 근거이자 관측면. `requested` 컬럼이 절삭 폭을 보존한다 |
  | 무플래깅 | **절삭 전** 요청량 > `10 × per-call` 이면 `profiles.flagged`. 절삭 후로 판정하면 캡이 스스로 증거를 지운다 |

  캡 값은 리터럴이 아니라 관측 가정에서 파생한다 —
  `60 런/h × 3 촉매/런 × 여유 2 = 360/h`. 런당 3은 `src/data/catalystDrops.ts` 파생
  (장비 2~3/런 × 게이트 상한 95%). 현실적 정직 피크(20런/h × 2 ≈ 40/h)의 9배라 정직한
  플레이를 막지 않는다. `CAP_GRANT_PER_CALL = 100` 은 **바꾸지 않았다** — 이 축의 결함은
  per-call 값이 아니라 누적 캡의 부재였고, 둘을 함께 흔들면 회귀 원인이 둘이 된다.

  **"서버가 정산 영수증에서 드랍을 파생" 은 검토 후 기각했다.** 이 ADR 자신의 논지("캡을
  방어선으로 쓰는 설계는 이미 기운 설계")를 따라 클라가 드랍량을 정하는 구조 자체를 없애는
  길을 먼저 봤으나, 그 길은 **신뢰 경계를 옮기지 못한다**: `catalystDropsFromRun` 의 입력은
  클라 sim 이 만든 장비 드랍 시드고 서버는 그 값을 갖고 있지 않다 — 파생을 SQL 로 옮겨도
  서버는 결국 클라가 보낸 시드 배열을 믿어야 하며, 위조 대상이 `{id, qty}` 에서 `{seed[]}` 로
  이름만 바뀐다. 오히려 시드→촉매 매핑이 순수·결정론이라 공격자가 원하는 희귀 촉매가 나오는
  시드를 오프라인 탐색할 수 있어 **무작위 적립이 표적 적립으로 나빠진다**.
  런 바인딩(settle 이 `run_id` 를 돌려주고 grant 가 그 런을 1회만 청구)도 함께 봤다 —
  `settle_pve_run` 역시 클라 호출 가능이라 verified 행을 얼마든지 찍어낼 수 있어 **그 자체로는
  유계가 아니고** 결국 누적 캡을 함께 요구한다. 누적 캡이 있으면 런 바인딩의 한계 이득은
  "12장당 RPC 1회 더"뿐인데 대가로 settle 반환 계약과 클라 정산 경로를 건드린다.

  **검증**: `tests/catalystGrantCapContract.test.ts`(누적 캡·원장·GC TTL>창·잠금 순서 3종·
  플래깅 기준·캡 파생) — 뮤테이션 6종(캡 제거·잠금 역전·TTL 24h·절삭 후 플래깅·원장 기록 삭제·
  캡 상수 하드코딩)이 전부 빨개지는 것을 확인했다.
  **원격 실증**: `scripts/prove-catalyst-grant-cap.ps1` — `set local role authenticated` +
  위조 JWT claims 로 클라 컨텍스트에서 태워, 500 을 요청해 **360 만 받는** 것을 확인했다
  (Management API 는 `postgres` 로 실행돼 `is_service_role()` 이 가드를 통과시키므로 적용
  스크립트만으로는 "가드가 있다"까지만 보이고 "문다"는 못 본다).

  **남은 사각(정직하게 기록한다)**: 원장은 실적립이 있을 때만 행을 남기므로(`grant_currency`
  와 같은 규율 — 0 적립 로그로 원장·GC 를 오염시키지 않기 위해) "캡에 부딪혀 0 을 받아간
  반복 호출"은 흔적이 없다. 그 신호가 필요해지면 별도 카운터를 두어야 한다.
- **ⓑ 크레딧 유입 재검토 — 밸런스 레인, 출시 전.**

  빼고 수급을 다시 계산해야 한다.
