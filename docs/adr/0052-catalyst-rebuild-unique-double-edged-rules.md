## ADR-0021 개정 — 특산 18종이 모드 계약의 두 조항과 만난다

특산 18종은 행성 모드 6종을 전제로 설계됐고, 그중 **7종**(30·33·36·38·42·45·47)이 모드의
**완주 조건 자체**를 바꾼다(처치 할당 절반 · 안전 원 점프 · 대피소 확보 2배 · 대피소 파괴 ·
정화율 절반 · 블록 경도 3배 · 스크롤 가속). 그리고 **18종 전부**가 모드 문맥에서 드랍을 얹는다.

ADR-0021 과 부딪히는 지점은 정확히 둘이다(진행 게이트 자체는 원문이 이미 "환경"에 포함시켰다):

1. **본문 §경계** — *"드랍/자원 획득"* 이 **공통 코어(전 행성 불변)** 로 명시돼 있다.
2. **§Consequences 첫 항** — *"모드 정체성은 영구 스탯 축 추가가 아니라 런 내 «모드 보정
   파워업»으로만 표현한다 — 임시라 런 종료 시 소멸하고 영구 경제를 오염시키지 않는다."*
   촉매는 **런 외부에서 고르는 영구 자원**이라 이 문장과 정면으로 만난다.

**개정 내용**: 위 두 조항에 **촉매 예외**를 연다. 모드 정체성을 촉매가 표현할 수 있고, 촉매는
모드 문맥에 따라 드랍과 완주 조건을 바꿀 수 있다.

**개정하지 않는 것 — 경계는 좁게 연다**:

- **조작 코어는 여전히 불변**이다(기체 이동·자동공격·판정점). ADR-0021 의 근거 ①(아이템 배제 0)
  은 이 축에 걸려 있고 촉매는 이 축을 건드리지 않는다.
- **간선 방향을 뒤집는다** — `src/sim/modes/*` 는 드랍·촉매를 **import 하지 않는** 순수 환경
  함수로 남고, **`src/sim/catalystHooks.ts` 가 모드 상태를 읽어** 드랍·게이트 보정을 얹는다.
  그래서 `modes/AGENTS.md` 의 *"모드가 바꿔도 되는 것은 환경뿐"* 규율과 그 파일의 내부 의존성
  목록(§54)이 **문자 그대로 유지된다.** 이것이 "규율을 없애지 않고 개정을 최소화하는" 방식이다.
- **아이템 배제 0 목표는 유지된다** — 촉매는 선택적이고 런당 3장이라, 어떤 아이템도 특정
  모드에서 무용해지지 않는다는 보증을 깨지 않는다. 촉매를 안 끼면 ADR-0021 원문 그대로다.
- **런 종료 시 소멸 규율은 촉매 자신에게도 적용된다** — 촉매가 만드는 것은 그 런 안의 규칙이고,
  영구 스탯 축을 새로 만들지 않는다(ADR-0052 §양날 규칙의 전제와 같다).

⚠️ **§페널티 금지 ④(진행 교착)와의 접점**: 게이트를 **느리게/불안정하게** 만드는 33·38·42 는
이 개정으로 허용되지만, 교착(완주 불가)을 만들면 여전히 금지다. 특히 **id 47**(스크롤 가속)은
blockBreak 코스가 `SEGMENTS.length - 1` 파생 길이로 **미리 깔려 있어**, 창이 코스 끝을 지나
벽 없는 빈 공간으로 나아가는 실패 모드가 있다(`waves.ts:376-384` 가 격전 사례로 하네스 실측
5,700틱 전진 0 을 남겼다 — **동형**이다). 배선 레인이 코스 길이를 함께 늘리지 않으면 안 된다.

ADR-0029 가 세운 촉매 48종은 전량 `(보상축 1개 +perStack, 페널티축 1개 +perStack)` 두 칸짜리
태그였고, 계수마저 상수 4개(`REWARD_PER_STACK 0.15` · `RESOURCE_PER_STACK 0.15` ·
`POWER_PER_STACK 0.1` · `PENALTY_PER_STACK 0.2`)에서 나와 **촉매 간 수치 차이가 0**이었다.
서로 다른 것은 이름과 아이콘뿐이고, 실제 차이는 6×6 격자에서 어느 칸을 집었는가에 그친다.
게다가 스택 수학이 축별 **선형 가산**이라 촉매끼리 상호작용이 원리적으로 0이다 — 4장을
발라도 독립된 덧셈 4번이라 "조합"이 성립할 수 없는 구조였다.

ADR-0049 가 스킬에서 밟은 것과 같은 전환을 촉매에 적용한다: **스탯 배율 → 유니크 메커닉**.
48종 전부를 **한 개의 양날 규칙**으로 다시 쓰고, 조합의 재미는 인위적 짝 정의가 아니라
규칙 간 창발 상호작용에서 나오게 한다.

## 결정

- **한 장 = 한 개의 양날 규칙**. 보상·페널티를 두 칸에 나눠 적지 않는다. 하나의 개념이
  이득과 대가를 동시에 품는다(예: "적이 죽을 때 폭발한다 — 그 폭발은 너도 태운다").
  `RewardAxis`·`PenaltyAxis` 6+6 격자와 `perStack` 스칼라 모델을 폐기한다.
- **유니크 주입 — 같은 촉매 중복 금지**(ADR-0029 §스택 번복). 규칙은 "2장이면 2배"가
  성립하지 않는다. 중복 보유분은 기존 분해 경로(ADR-0042)로 잔재가 된다.
- **슬롯 상한 8 → 3**. 규칙 여덟이 동시에 돌면 무엇이 무엇 때문인지 읽히지 않아 학습이
  일어나지 않는다. 3장은 48C3 = 17,296 조합으로 충분히 넓으면서 인과가 읽히고,
  **정산 캡 합성이 현행 서버 구조 안에 들어온다**(합산 규약 최악 ×3.25 — 4장이면 ×3.94 로
  기준선을 넘겨 `CAP_HOURLY_CREDITS` 재도출이 따라온다). 특산은 한 런에 최대 2장이다.
- **페널티는 플레이어의 조작·전략을 직접 제약할 수 있다**. 적 스탯 배율만으로는 체감이
  "적이 좀 세짐" 하나로 수렴한다. 재장전 불가·자동조준 해제·대피소 소멸·스킬 비용 전환
  같은 플레이 방식 변경을 허용한다(Hades 징벌 서약 문법).
- **경제 이득은 규칙 안에 조건부로 내장한다**. 무조건 배율을 달지 않는다 — 플레이어가
  버는 액수가 실력·빌드에 따라 변해야 기술 표현이 생긴다.
- **정산 캡은 촉매별 "이론적 최대치" 선언으로 미러한다**. 서버는 조건부 보상의 실제 액수를
  예측할 수 없으므로, 각 규칙이 최상의 시나리오에서 만들 수 있는 자원·드랍 배율 상한을
  상수로 선언해 `catalyst_defs` 에 미러하고 `settle_pve_run` 은 그 상한만 강제한다.
  기존 `CATALYST_RESOURCE_MIRROR` 구조와 계약 테스트를 그대로 잇는다.
- **특산 18종은 행성 모드를 극단으로 비트는 규칙**이다. ADR-0029 가 선언만 하고 배선하지
  않아 `src/` 어디에서도 읽히지 않던 `modeHook` 을 실제 배선한다. 특산이 그 행성 전용인
  대가로 받는 것이 여기서 처음 생긴다.
- **가시성이 채택의 전제조건이다**. 런 중에 전용 신호(이펙트·색·음·적 외형 변화 등)를
  갖지 못하는 아이디어는 설계안에서 탈락시킨다. 이 규율이 "숫자만 올리는" 아이디어를
  구조적으로 걸러낸다.
- **파워 분포는 상황 의존을 주축으로 한다**. 무조건 강한 촉매를 두지 않는다. 모든 규칙은
  특정 행성·모드·기체 빌드·다른 촉매와 맞물릴 때만 강해진다.
- **조합은 창발 주축 + 태그 공명 소량**. 48종 짝을 수동 정의하지 않는다. 촉매마다 태그
  1~2개를 달고, **같은 태그 2장 = 약공명 / 3장 = 강공명**이 발동한다(2단). 공명도 규칙이며
  전용 신호와 상한을 갖는다.
- **id·slug·아이콘 48장은 그대로 유지한다**. 서버 원장(`catalyst_inventory`)·상점 가격
  시드·i18n 키·개별 아트가 전부 이 앵커 위에 서 있고, slug 의 의미(풍요·약탈·정련·연쇄
  반응…)는 오히려 규칙 저작의 좋은 제약이다.

## 귀결

- **골든 전량 재생성 + EF 재배포**. 규칙형은 sim 거동을 바꾸므로 `pnpm test:sim` 3파일과
  `verify-invasion`·`verify-commission` 재배포가 따라온다(공통-C). 촉매 폴드는 ADR-0029
  이래 **조건부 꼬리**라 무촉매 런·침공 런은 바이트 불변이 유지된다.
- **서버 마이그레이션 3건**: `catalyst_defs` 스키마(자원 배율 1칸 → 이론적 최대치 다축) ·
  `consume_catalysts` 의 **SLOT_CAP 8→3** · **중복 거부**·**특산 최대 2장** 게이트 신설 ·
  영수증 포맷 확장. ⚠️ **`CAP_RESOURCE_MULT_MAX` 는 캡이 아니라 클램프이고 파생식이다**
  (`ledger.sql:221` `1 + SLOT_CAP × MAX_RESOURCE_PER_STACK`) — `SLOT_CAP` 을 3으로 바꾸면
  1.45 로 **더 내려가** 설계 상한을 영수증 단계에서 잘라낸다. **파생식을 폐기하고 리터럴로
  대체**해야 한다.
- **기존 유저 보유분은 무손실이되 의미가 바뀐다**. 원장은 id 기준이라 수량이 보존되고,
  유니크 주입 전환으로 잉여가 된 중복분은 상점 분해로 흡수된다(자동 환급 마이그레이션은
  하지 않는다 — 분해는 유저의 선택이고 경로가 이미 있다).
- **밸런스 "출시 전 일괄 튜닝" 방침이 이 축에서는 부분적으로 깨진다**. 규칙은 계수가
  아니라 존재 자체가 밸런스라, 상황 의존 파워 분포는 `pnpm bench:*` 를 **상황별로** 돌려
  재야 한다(평균 하나로는 안 끝난다).
- `catalystSummary.ts`·`catalystLabels.ts` 의 "축별 배율 줄" 모델이 통째로 무효가 된다 —
  픽커·HUD 표시는 규칙 카드 목록 + 공명 상태로 다시 쓴다.

## 기각한 대안

- **축을 6+6 → 20+20 으로 확장**: 공사가 작고 계약이 안 깨지지만, 여전히 "숫자 두 개"라
  조합 상호작용이 원리적으로 생기지 않는다. 사용자 문제 제기의 핵심을 안 건드린다.
- **2계층(수치형은 스택, 규칙형은 유니크)**: ADR-0029 번복 범위가 작지만 플레이어가 두
  문법을 동시에 외워야 하고 UI 가 갈라진다.
- **명시적 짝/세트 중심 조합**: 발견의 기쁨이 가장 진하나 48종의 짝을 수동으로 설계·밸런
  스·테스트해야 해 유지보수가 폭발한다.
- **24종으로 압축**: 장당 밀도는 가장 높지만 아이콘 24장이 버려지고 드랍풀·특산 6행성×3
  구조를 다시 짜야 한다.
- **단계적 도입(대표 16종 먼저)**: 리스크가 낮으나 구/신 문법이 공존하는 중간 상태가
  길어진다. 사용자가 48종 전원 유니크를 명시적으로 선택했다.
- **조건부 보상의 서버 사후 검증**(클라가 조건 달성 증빙 제출): 가장 정밀하지만 새 증빙
  포맷과 검증 로직이 통째로 필요하고, PvE 리플레이 검증을 폐기한 ADR-0026·ADR-0050 의
  방향과 역행한다.

## 진행 방식

①설계 헌장 + 48종 카탈로그 저작 → ②비평가 에이전트 반복 평가(유니크함·조합 깊이·가시성·
구현 가능성·경제 안전성) → ③사용자 최종 심사 → ④구현 레인 분할(타입·데이터 계층 →
sim 배선 → 연출 → UI → 서버 마이그레이션). 수치는 러프하게만 잡는다.
