# 밸런스 체크 (`pnpm balance`)

한 번 실행하면 **10분 안에** 난이도 곡선 · 로스터 편차 · 행성 편차 · 경제 지표를 한꺼번에
재고 게이트로 판정한다. 새 행성 · 새 기체 · 새 장비 · 새 아이템이 들어와도 **하네스를 고칠
필요가 없다** — 축이 카탈로그에서 파생되고, 격자가 커지면 표본이 자동으로 줄어 소요 시간이
유지된다.

```bash
pnpm balance
```

---

## 1. 무엇을 재는가

측정 단위는 **격자 한 칸**이다:

```
셀 = (행성, 기체, 표준 레벨)
```

각 셀을 **표준 빌드**(그 레벨의 표준 장비 · 표준 스킬 투자 · 대응 침략 단계 `ceil(Lv/5)`)로
결정론 오토파일럿(ADR-0008)이 돌고, 셀마다 시드를 여러 개 굴려 통계를 낸다.

이 리포가 따로 재던 세 지표는 전부 **같은 격자의 다른 접기**다:

| 리포트 | 접는 축 | 예전 방식 |
|---|---|---|
| 난이도 곡선(ADR-0037 합격선 60~80%) | 레벨 | `rosterBench --curve`, 1,920런 순차 |
| 로스터 편차(M8) | 기체 | `rosterBench` 매트릭스, 2,016런 순차 |
| 행성 난이도 편차 | 행성 | 임시 vitest 파일로 매번 새로 작성 |

그래서 스윕을 **한 번만** 돌면 세 리포트가 동시에 나온다.

## 2. 왜 10분에 끝나는가

세 가지가 겹쳐 성립한다.

### ① 병렬 실행

sim 을 `vite build --ssr` 로 단일 `.mjs` 로 묶고(`vite.balance.config.ts`) `node:worker_threads`
로 **코어 수 − 2** 개 워커에 뿌린다. 16코어 머신 기준 14배.

> 예전에는 `vite-node` 가 없어 측정할 때마다 임시 vitest 파일을 손으로 짜야 했고(재현 불가),
> vitest 는 **파일 단위로만** 병렬화돼 한 파일 안의 스윕은 단일 스레드로 돌았다.

### ② 라운드 단위 시드 확장 + 예산 감시

한 라운드 = **모든 셀을 시드 1개씩**. 라운드가 끝날 때마다 남은 예산과 직전 라운드 소요를
비교해(`decideNextRound`, 안전계수 1.25) 다음 라운드를 돌릴지 정한다.

- 예산 초과가 **구조적으로 불가능**하다 — 다음 라운드를 시작하기 *전에* 판단한다.
- 어느 시점에 멈춰도 표본이 **모든 셀에 고르게** 깔려 있다(라운드 경계에서 멈추므로).
- 라운드 안에서는 직전 라운드 소요 내림차순(LPT)으로 배분해 라운드 꼬리를 줄인다.

### ③ 머신 실측 캘리브레이션

시작 직후 층화 미니 격자로 **이 머신의 틱당 비용과 런당 평균 틱**을 재고, 그 값으로 예산이
감당할 셀 수를 계산한다(`affordableCells`). 격자가 그보다 크면 축을 균등 간격으로 솎는다
(`shrinkAxes` — 각 축의 **양 끝은 보존**, 최소 2점 유지).

즉 **하드웨어 상수가 리포에 박혀 있지 않다.** 느린 머신에서는 표본이 줄고, 빠른 머신에서는
늘어난다. 어느 쪽이든 10분에 끝난다.

## 3. 새 콘텐츠가 들어올 때 고칠 것

| 새로 들어오는 것 | 하네스 수정량 | 근거 |
|---|---|---|
| **행성** | **0** | `PLANETS` 레지스트리에서 축을 뽑는다 |
| **기체** | **0** | `SHIP_TYPES` 동상 |
| **장비 · 어픽스 · 유니크** | **0** | 표준 세트가 정본 `rollItem` 을 그대로 굴린다 |
| **스킬 노드** | **0** | 표준 투자가 `flattenShipNodes` 에서 파생된다 |
| **만렙 상향 · 밴드 재정의** | **0** | `BAND_LEVELS` 가 `LEVEL_CAP` / `LEVEL_PER_STAGE` 에서 파생된다 |
| **런 입력(촉매·의뢰 등)** | **0** | `buildRunConfig` 단일 정본을 거치므로 기본값이 자동 반영. 그 축을 **변인으로 쪼갤 때만** `axes.ts` 에 축을 하나 추가 |
| **새 지표** | **1줄** | `metrics.ts` 의 `RUN_METRICS` 에 한 줄. 집계·표·게이트가 전부 이 객체를 순회한다 |
| **새 게이트** | **0줄**(위와 동시) | 지표에 `target` 을 적으면 게이트가 자동 생성된다 |

`tests/balanceHarness.test.ts` 가 이 계약을 지킨다 — 누군가 축을 하드코딩 목록으로 되돌리면
테스트가 깨진다. (이 리포가 반복해서 겪은 결함이 정확히 "카탈로그는 늘었는데 목록이 안 늘어
조용히 빠짐"이다.)

**축이 늘어난 대가는 시간이 아니라 표본 정밀도다.** 행성이 6→8 이 되면 소요는 그대로고 셀당
시드 수가 줄어든다.

## 4. 게이트

`src/bench/balance/metrics.ts` 의 `target` 이 정본이다. 2026-08-01 현재:

| 지표 | 밴드 | 범위 | 근거 |
|---|---|---|---|
| 클리어율 | 60~80% | **레벨별** | ADR-0037 표준 빌드 합격선 |
| 클리어초 | 60~190s | 전체 | `RUN_SECONDS_PAR = 95` 의 0.63~2.0배 |
| 타임아웃 | 0~2% | **레벨별** | 구조 건전성(18,000틱 상한에 걸리는 런은 사실상 없어야 한다) |
| 런내 레벨업 | 5~8 | 전체 | ADR-0036 개정 2 |
| 장비유입 | 2~3 | **완주 런** | ADR-0035 §3.1 |

표본이 0 인 지점은 **위반이 아니라 미판정**으로 센다(승리 0건인 셀의 클리어초를 위반으로
세면 "너무 빠르다"는 거짓 신호가 된다).

### ⚠️ 밴드의 **모집단**도 정본과 맞춰라 (`kind`) — **해소됨(2026-08-03)**

`scope` 가 "어느 축으로 접어 볼 것인가"라면 `kind` 는 "어떤 런을 셀 것인가"다. 둘 다 틀릴 수 있다.

`lootPerRun` 이 그 예였다. 밴드의 정본(ADR-0035 §3.1)은 **완주 런** 기준 셈인데(보스 확정 1 +
엘리트 기대 1.5) 지표는 `mean`(전 런)이었다. 패배 런은 보스 드랍이 없으므로, **승률이 낮아질수록
장비유입 게이트가 빨개진다** — 드랍 축을 하나도 건드리지 않아도 그렇다. 즉 이 게이트는 드랍
설계가 아니라 승률을 재고 있었다.

두 정의는 **동시에 만족될 수 없다**: 전 런 평균을 2.0 위로 올리려면 드랍 목표를 1.5 → 2.6 으로
올려야 하고, 그러면 완주 런이 4.38개가 되어 `tests/drops.test.ts` 의 통합 가드가 빨개진다(실측).

**해소**: 지표를 정본 쪽(`kind: 'winMean'` = 완주 런)으로 맞췄다(main `4709e74`, 밸런스 큐 §R14).
같은 회차에 봇 전리품 수거도 신설돼 계측기가 두 겹으로 고쳐졌다. 지금 이 게이트가 빨간 것은
**진짜 드랍/수거 미달**이라는 뜻이고 승률과 혼선되지 않는다 — 전체 격자 4,620런 확정 실측
**1.91**(밴드 2~3, 하한에 0.09 미달)이고 남은 미달분은 드랍이 아니라 **수거 실패**다(밸런스 큐 §R25).

**교훈은 남는다: 밴드를 적을 때 그 수치가 어느 모집단에서 나온 값인지 먼저 확인해라.**

### ⚠️ `scope` 를 고르는 법 — 전체 평균은 국소 이상을 가린다

`scope` 는 `'overall'`(기본) 또는 축 이름(`'level'`·`'planet'`·`'ship'`)이다. 축을 주면 **그
축으로 접은 점마다** 판정하고, 위반 지점이 리포트에 이름으로 찍힌다.

`timeoutRate` 가 이 선택이 왜 중요한지 보여준다. `'overall'` 이던 동안 전체 0.8% 로 **게이트가
초록이었는데**, 레벨별로 보니 **Lv100 만 10.6%**(그중 니플헤임 44.8%)였다 — 만렙 추격 런의
절반 가까이가 5분을 넘겨도 끝나지 않고 있었다.

**새 지표에 `target` 을 달 때 먼저 답해라: 이 성질이 전체 평균으로 성립하면 충분한가, 아니면
구간마다 성립해야 하는가.** 구조 건전성·난이도 곡선처럼 "어디서나 참이어야" 하는 축은 반드시
축 단위로 본다.

### 게이트가 없는 진단 지표 (판정은 안 하되 처방을 가른다)

| 지표 | 무엇을 가르는가 |
|---|---|
| `보스도달초`(`bossReachSec`) | **무대 페이싱의 정본.** 목표는 90초(2026-08-01 지시). `클리어초` 는 보스전 소요를 포함해 이 목표를 직접 재지 못한다 |
| `장치잔존`(`chaseDevicesLeft`) | 추격 타임아웃이 "장치를 못 깬 것"인지 "취약화 후 못 잡은 것"인지 |
| `미수거전리품`(`lootGround`) | 장비유입 부족이 **드랍이 적은 것**인지 **줍지 못하는 것**인지 |
| `맵상실`(`mapLossRate`) | 패배가 **플레이어 사망이 아닌** 비율(오염 임계 · 무적 포식자 접촉 즉사). 크면 처방이 확산 시계·포식자 접근 쪽이다 |
| `정화율`(`purifyEnd`) | 오염 무대의 목표 진척. 패배 런에서 낮게 고이면 사인은 압박이 아니라 **목표 총 HP** 다 |
| `지형피해분`·`접촉피해분` | 잃은 HP 의 귀속. 잔차(1 − 둘)는 원거리 탄 + 직접 피해(압사·압박) |

⚠️ `보스도달초` 는 **승리 런만** 본다(`winPosMean`). 승률이 낮은 무대에서는 "빨리 깬 런"만
표본에 남아 값이 **아래로 편향**된다 — 톡사르에서 같은 설정이 3분 단일 행성 런 63.8초 · 8분
전체 격자 94.2초로 갈렸다. **승률이 낮은 무대의 페이싱 수치는 승률을 고친 뒤 다시 재라.**

### 레버가 연결돼 있는지 먼저 확인해라

이 리포는 "**레버를 4배로 돌렸는데 결과가 10% 움직이는**" 상황을 두 번 겪었고, 두 번 다 원인이
밸런스가 아니라 **그 오브젝트가 자동 조준 대상이 아니었다**는 것이었다(추격 반격 장치 · 오염
노드). 수치를 더 올리기 전에 **입력 대비 출력의 크기**를 먼저 보라 — 비례하지 않으면 그 축은
연결돼 있지 않은 것이고, 계속 올리면 없는 문제를 튜닝하게 된다. 목표 오브젝트 판정 정본은
`src/sim/modes/objective.ts` 다.

### 집계 규칙만 바꿔 다시 해석하기 (재측정 없음)

```bash
node scripts/balance/run.mjs --no-build --reanalyze=.balance/final
```

`runs.json` 을 다시 읽어 리포트·요약만 재생성한다. 시뮬레이션을 한 번도 돌리지 않으므로
몇 초면 끝난다. 위 `timeoutRate` scope 수정이 실제로 이 경로로 검증됐다 — 지표 정의나 게이트
밴드를 손봤을 때 10분을 다시 쓸 필요가 없다.

## 5. 사용법

```bash
pnpm balance
```

```bash
pnpm balance:quick
```

주요 인자(`pnpm balance -- --인자` 형태로 준다):

| 인자 | 뜻 |
|---|---|
| `--minutes=N` / `--seconds=N` | 예산(기본 10분) |
| `--workers=N` | 워커 수(기본 코어−2) |
| `--planets=0,3` `--ships=0` `--levels=5,50,100` | 축 부분 선택 |
| `--powerups=0,1,2,3,4` | **파워업 정책 축을 연다**(§8). 미지정이면 축 자체가 없다 — 기본 격자와 바이트 동일 |
| `--min-rounds=N` | 격자 축소 시 지키려는 셀당 시드 수(기본 8) |
| `--max-rounds=N` | 셀당 시드 상한(기본 96) |
| `--out=DIR` | 산출 폴더(기본 `.balance`) |
| `--gate` | 게이트 실패 시 exit 1 (CI용) |
| `--no-build` | 직전 번들 재사용 |
| `--verbose` | 라운드마다 로그(기본은 5초에 한 줄) |
| `--reanalyze=DIR` | `DIR/runs.json` 을 다시 집계해 리포트만 재생성(시뮬 미실행) |

## 5.2 회차를 굴리는 법 — **이 절을 먼저 읽어라**

한 회차 = "한 축을 바꾸고 전후를 같은 표로 대조한다". 아래는 그 회차의 비용을 최소로 굴리는
절차다. 2026-08-02 레인이 이걸 안 지켜서 측정 자체보다 **주변 작업에 시간과 토큰을 더 썼다.**

### ① 프로브는 **시험 중인 행성만** 좁혀서 3분

```bash
pnpm balance:probe -- --planets=2,4 --out=.balance/probe-a
```

**격자를 좁히면 시간이 줄 뿐 아니라 정밀도가 오른다.** 예산은 라운드 단위로 쓰이고 격자가
예산보다 크면 축을 솎으므로(`shrinkAxes`), 격자를 좁히면 그 솎아냄이 줄어든다. 실측(2026-08-02,
같은 머신):

| | 소요 | 시드 | 레벨 축 | 행성당 런 |
|---|---|---|---|---|
| 전 행성 `pnpm balance` | 10분 | 14 | **5점으로 솎임**(5·25·60·80·100) | 490 |
| 2행성 `pnpm balance:probe` | **2.8분** | 14 | **10점 전량** | **980** |

시간은 1/3 인데 행성당 표본은 2배이고, **레벨 축이 솎이지 않는다** — 클리어율 게이트가 레벨별
판정이므로 이게 특히 중요하다.

⚠️ **그래서 프로브 수치를 전 행성 런 수치와 직접 비교하면 안 된다.** 레벨 축이 다르면 모집단이
다르다 — 같은 코드에서 니플헤임이 프로브 38.8% / 전 행성 40.8%, 톡사르 21.6% / 24.5% 로 갈렸다
(프로브가 Lv15·35·45·70·90 을 포함하기 때문이지 무엇이 바뀌어서가 아니다). **프로브는 프로브끼리,
전 행성 런은 전 행성 런끼리** 대조해라(`compare.mjs` 는 시드만 맞추지 축 구성까지는 못 맞춘다).

전 행성 10분 런은 **확인 라운드에서 한 번만** 쓴다(대조군까지 포함해 최종 수치를 확정할 때).

### ② 전후 대조는 손으로 집계하지 마라

```bash
pnpm balance:compare .balance/before .balance/after --levels
```

밸런스 큐에 붙일 한글 마크다운 표는 `--md` 로 뽑는다.

이 스크립트가 자동으로 하는 두 가지가 중요하다:

- **공통 시드로 잘라서 비교한다.** 두 회차는 예산 안에서 도는 라운드 수가 달라 시드 수가
  어긋난다(실측 13 vs 14). 그대로 비교하면 축을 건드리지 않은 행성까지 움직여 **대조군이
  성립하지 않는다.**
- **대조군을 `(셀, 시드)` 단위 런 대조로 판정한다.** 집계 평균 비교로는 안 된다 — `runs.json`
  배열 순서가 달라 부동소수 합산 순서가 바뀌고, 완전히 동일한 런 집합에서도
  `90.53109649122808` vs `…811` 로 갈린다. 출력의 `control (run-for-run identical)` 에 **축을
  안 건드린 행성이 전부 들어와 있어야** 그 레버가 모드 게이트 안에 있다는 증거가 된다.

### ③-0 ⚠️ 레인 끝에는 **`pnpm test:sim` 도 돌려라** — 기본 스위트는 침공을 안 본다

`tests/invasionBalance.test.ts`(침공 밴드) · `commissionBandMeasure`(의뢰 계급) · 골든 해시 ·
완주 e2e 는 **기본 vitest 스위트에서 제외돼 있다**(`vite.config.ts` 의 `SIM_LANE_FILES` 8개).
그래서 **"전체 스위트 275파일 초록"이 침공을 한 번도 안 돌린 상태와 구분되지 않는다** —
2026-08-03 레인이 실제로 그 착각을 했다(사용자 지적으로 발견).

밸런스를 만졌으면 반드시:

```bash
pnpm test:sim
```

⚠️ **실패 수만 보고 놀라지 마라.** main 기준으로 이미 8파일 58건이 깨져 있다(골든 재생성 대기).
내 변경 탓인지는 **레인 시작 커밋을 `git checkout` 해서 같은 명령을 돌리고 파일별 실패 수를
나란히 놓아야** 안다. 20분 × 2회지만 이것 말고 판별할 방법이 없다.

### ③ 회차 중에는 전체 `vitest` 을 돌리지 마라

전체 스위트는 이 리포에서 **약 19분**이다(262파일 · 5,782케이스). 회차 중에는 관련 파일만 돌리고,

## 5.1 지표를 모드 사이에서 읽을 때 (⚠️)

**모드마다 같은 이름의 사건이 다른 것을 가리킨다.** 지표를 무대 간에 나란히 놓을 때 같은 것을
세고 있다고 가정하지 마라.

`보스교전`(`bossReachRate`)이 그 예다. 정의는 "**교전 가능한** 보스 엔티티를 본 적이 있는가"이고
모드별 실체는 이렇다:

| 모드 | 보스에 이르는 경로 |
|---|---|
| 뱀서류 · 수축 · 오염 · 레이싱 · 블록격파 | 웨이브를 다 헤쳐 보스 세그먼트 진입 → 보스 스폰 |
| **추격**(니플헤임) | 포식자가 **런 시작부터 존재**하되 무적. 반격 장치 5개를 다 깨야 취약화(`aux0=1`)되고 그때부터 교전 가능 |

처음 구현은 이 지표를 `state.wave.boss`(웨이브 디렉터가 보스 세그먼트인가)로 정의했는데,
추격 모드는 **승리조차 그 세그먼트에 닿기 전에 성립한다**(승리 = 취약화된 포식자 처치, 세그먼트
전진은 대피소 도달로 별개). 결과는 니플헤임 2,240런 중 **승리 422건이 전부 `보스교전=0`** 이었다 —
게이트는 통과하는데 지표가 아무것도 보지 않는 상태였다.

판정은 `src/bench/balance/cell.ts` 의 `bossEngageable` 하나에 모여 있고,
`tests/balanceHarness.test.ts` 의 **"승리 런은 보스를 관측한다"** 불변식이 이 부류의 재발을
막는다(PvE 승리는 곧 보스 처치이므로 구조적으로 참이어야 한다).

**새 모드를 추가할 때**: 그 모드의 승리·진행 경로가 기존 지표 정의와 어긋나는지 먼저 확인하고,
어긋나면 `bossEngageable` 처럼 **판정을 한 곳에 모아** 모드 분기를 넣어라.

## 6. 이 측정이 덮지 못하는 것 (자인)

- **액티브 스킬은 발동되지 않는다.** `autopilotInput` 이 `special` 로 파워업 선택만 낸다
  (`src/sim/autopilot.ts`). 액티브 축(ADR-0041)은 이 격자에 들어오지 않는다. 봇에 발동이
  들어오면 `src/bench/balance/cell.ts` 에 표준 액티브 세트 한 줄만 추가하면 된다.
- **봇의 전리품 수거는 반경 900 안으로 제한된다**(2026-08-03 신설). 그 전에는 전리품·젬을 향한
  이동이 **아예 없어서** `lootPerRun` 이 드랍 설계가 아니라 봇의 무관심을 재고 있었다(수거 1.21
  + 바닥 0.99 = 2.2 로 설계 기대값과 일치했다). 지금도 사람만큼 줍지는 않는다 — 이 지표의
  절대값은 여전히 하한으로만 읽어라.
- **봇은 최적 플레이가 아니다.** 카이팅 + 탄 회피 휴리스틱이라(ADR-0008) 절대 클리어율은
  사람보다 낮다. 이 리포트가 판정하는 것은 절대값이 아니라 **축 간 상대 난이도와 밴드 이탈**이다.
- ~~**파워업 선택은 항상 0번**이다.~~ → **재게 됐다(2026-08-03, §8 참조).** 기본 격자는 여전히
  오퍼 0번이지만(그래야 기존 실측과 대조가 성립한다) `--powerups=0,1,2,3,4` 로 **정책 축을 열면**
  파워업 선택이 클리어율을 얼마나 가르는지 수치가 나온다. 남은 자인은 **진짜 0-파워업 대조군이
  구조적으로 불가능**하다는 것이다(레벨업 프리즈는 유효한 픽 없이는 안 풀린다) — 최약 근사
  정책으로 대신한다.
- **표준 장비는 시드당 한 벌이 아니라 `(기체, 시드)` 당 한 벌이다**(2026-08-02 수정,
  `cell.ts` `gearSeed`). 예전에는 `standardEquipped` 가 기체를 안 받아 한 시드 안에서 기체
  7종이 **같은 장비**로 돌았고, 그래서 `(행성, 레벨)` 한 점의 유효 표본이 √7 배 부풀려져
  **장비 운이 레벨 곡선의 굴곡으로 위장**했다. 대신 기체 비교의 짝짓기(장비 통제)를 잃는다 —
  로스터 편차는 기체당 수백 런으로 접어 그 운이 평균되므로 그쪽이 손해가 작다.
- **침공(PvP)·의뢰 런은 이 격자에 없다.** 각각 `tests/invasionBalance.test.ts` 와 의뢰 계측이
  별도 축이다.

## 8. 선택 축 — 기본 격자를 건드리지 않고 여는 변인

두 축은 **명시할 때만** 열린다. 미지정이면 셀에 그 필드가 붙지 않고, 런·`runs.json`·리포트가
축 신설 전과 **바이트 동일**하다(`tests/balanceHarness.test.ts` 의 교환 대조가 못 박는다).

### ① 파워업 정책 (`--powerups=`)

```bash
node scripts/balance/run.mjs --no-build --minutes=6 --levels=5,25,50,75,100 --powerups=0,1,2,3,4 --out=.balance/pw
```

| id | 정책 | 무엇을 고르는가 |
|---|---|---|
| 0 | 기준선(0번) | 오퍼 0번 — **현행 오토파일럿과 동일**. 이 축의 대조 기준 |
| 1 | 화력우선 | 오퍼 중 무기 스탯 계열 |
| 2 | 생존우선 | 최대 HP 계열 |
| 3 | 기동우선 | 이동·대시·젬 반경 계열 |
| 4 | 최약근사 | 기동 → 생존 → 화력 순 — **0-파워업의 근사 대조군** |

**계열은 하드코딩이 아니라 `apply` 의 실제 변이를 관찰해서 정한다**(`src/bench/balance/powerupPolicy.ts`).
새 파워업이 `POWERUPS` 에 append 되면 자동으로 분류되고, 분류가 안 되면 테스트가 **큰 소리로
실패**한다(조용한 미분류 = 그 파워업이 어떤 정책에도 안 걸려 영원히 안 뽑히는 상태).

> ⚠️ 그 관찰기가 신설 즉시 실물 **3종**을 잡았다. 닫힌 형식은 `c(1 − m) < 0.5` 이고, `fp-cadence`
> (×0.92)는 발사 간격 ≤ 6틱에서 무동작이라 **벌컨(6) · 빔(4)에서 처음부터 아무 일도 하지 않는다.**
> `rapid-fire`(×0.90)는 벌컨에서 6→5 한 번만 먹고 죽고(`Math.round(4.5) = 5`), `dash-coils`·
> `sv-evasion`(×0.92)은 대시 재충전 하한 12 에 닿는 순간 죽는다. 밸런스 큐 §R22 — **등재만 했고
> 고치지 않았다**(처방이 밸런스 변경이라 사용자 판단 항목).

**실측(1,050런 · 정책당 n=210)**: 클리어율 폭 **3.8pp** — 기준선 69.0 · 화력우선 65.7 ·
생존우선 69.5 · 기동우선 69.0 · 최약근사 67.6%. 행성 편차 24.7pp · 레벨 축 30pp 대에 비해
**한 자릿수 아래**다. ⚠️ 시드 1개라 비대조 SE ≈ 3.2pp — **폭이 SE 안이므로 순위를 주장하지 마라**
(등재된 것은 "폭이 크지 않다"는 상한이다). 역설 하나: 화력우선이 보스DPS 를 +27% 올리는데
클리어율은 가장 낮다 — 승패를 가르는 것은 보스 화력이 아니라 그 앞의 생존이다. 상세는 §R21.

**⚠️ 자인 — 진짜 "무-파워업" 런은 만들 수 없다.** 레벨업 프리즈는 유효한 픽이 올 때까지 월드를
정지시키고 범위 밖 인덱스는 프리즈를 소비하지 않는다(위조 프레임이 빌드 선택을 건너뛰지 못하게
한 고의 설계, `stepWorld`). 즉 픽을 안 내면 런이 타임아웃까지 얼어붙는다. 정책 4 는 그 대조군의
**근사**이며, 이 축의 값은 "파워업을 껐을 때"가 아니라 **"가장 약하게 골랐을 때"** 로 읽어야 한다.

**침공 밴드와의 관계.** `tests/invasionBalance.test.ts` 가 재는 승률은 통째로 **파워업 추첨 운의
분포**다(그 파일 헤더 ①) — 침공은 파워업 픽을 정책으로 고르지 않고 무엇이 뽑히느냐에 맡긴다.
이 축은 그 분산의 **크기를 PvE 격자에서 미리 재 주는** 역할이다: 정책 간 클리어율 폭이 크면
침공 승률 표본의 노이즈 하한도 그만큼 크고, 폭이 작으면 침공 밴드 이탈은 추첨 운이 아니라
방어 기지 강도 쪽이라는 뜻이다(밸런스 큐 §R7·§R18 의 갈림길). **두 축은 같은 레버(파워업
상한 −10%)를 공유하되 이쪽만 결정론으로 통제할 수 있다.**

### ② 침략 단계 override (`probe-stage.mjs --stages=`)

표준 격자는 `stage = ceil(Lv/5)` 로 레벨과 단계를 묶는다. 그래서 **둘을 떼어 놓아야만 답할 수
있는 질문**은 구조적으로 관측 불가능했다. 전용 프로브를 쓴다:

```bash
node scripts/balance/probe-stage.mjs --no-build --planets=0,1,2,3,4,5 --ships=0,2,4 \
  --levels=5,25,50,75,100 --stages=1,5,10,15,20 --seeds=6 --out=.balance/twink
```

두 용도가 있다: **트윙크 스톰프**(만렙이 낮은 단계를 도는 격차, 밸런스 큐 §R23 — 만렙의 단계
민감도가 **−10.2pp** 로 다른 레벨의 1/3~1/4 다)와 **`MIN_BOSS_KILL_TICKS` 실측**(Lv100 / 단계 1
최속 승리 — 표준 격자가 만들 수 없는 셀. 니플헤임 포함 재측정 결과 관측 최소 **315틱**, §R24).
