# 밸런스 체크 (`pnpm balance`)

한 번 실행하면 **10분 안에** 난이도 곡선 · 로스터 편차 · 행성 편차 · 경제 지표를 한꺼번에
재고 게이트로 판정한다. 새 행성 · 새 기체 · 새 장비 · 새 아이템이 들어와도 **하네스를 고칠
필요가 없다** — 축이 카탈로그에서 파생되고, 격자가 커지면 표본이 자동으로 줄어 소요 시간이
유지된다.

```bash
pnpm balance
```

---

## 1. 무엇을 재는가

측정 단위는 **격자 한 칸**이다:

```
셀 = (행성, 기체, 표준 레벨)
```

각 셀을 **표준 빌드**(그 레벨의 표준 장비 · 표준 스킬 투자 · 대응 침략 단계 `ceil(Lv/5)`)로
결정론 오토파일럿(ADR-0008)이 돌고, 셀마다 시드를 여러 개 굴려 통계를 낸다.

이 리포가 따로 재던 세 지표는 전부 **같은 격자의 다른 접기**다:

| 리포트 | 접는 축 | 예전 방식 |
|---|---|---|
| 난이도 곡선(ADR-0037 합격선 60~80%) | 레벨 | `rosterBench --curve`, 1,920런 순차 |
| 로스터 편차(M8) | 기체 | `rosterBench` 매트릭스, 2,016런 순차 |
| 행성 난이도 편차 | 행성 | 임시 vitest 파일로 매번 새로 작성 |

그래서 스윕을 **한 번만** 돌면 세 리포트가 동시에 나온다.

## 2. 왜 10분에 끝나는가

세 가지가 겹쳐 성립한다.

### ① 병렬 실행

sim 을 `vite build --ssr` 로 단일 `.mjs` 로 묶고(`vite.balance.config.ts`) `node:worker_threads`
로 **코어 수 − 2** 개 워커에 뿌린다. 16코어 머신 기준 14배.

> 예전에는 `vite-node` 가 없어 측정할 때마다 임시 vitest 파일을 손으로 짜야 했고(재현 불가),
> vitest 는 **파일 단위로만** 병렬화돼 한 파일 안의 스윕은 단일 스레드로 돌았다.

### ② 라운드 단위 시드 확장 + 예산 감시

한 라운드 = **모든 셀을 시드 1개씩**. 라운드가 끝날 때마다 남은 예산과 직전 라운드 소요를
비교해(`decideNextRound`, 안전계수 1.25) 다음 라운드를 돌릴지 정한다.

- 예산 초과가 **구조적으로 불가능**하다 — 다음 라운드를 시작하기 *전에* 판단한다.
- 어느 시점에 멈춰도 표본이 **모든 셀에 고르게** 깔려 있다(라운드 경계에서 멈추므로).
- 라운드 안에서는 직전 라운드 소요 내림차순(LPT)으로 배분해 라운드 꼬리를 줄인다.

### ③ 머신 실측 캘리브레이션

시작 직후 층화 미니 격자로 **이 머신의 틱당 비용과 런당 평균 틱**을 재고, 그 값으로 예산이
감당할 셀 수를 계산한다(`affordableCells`). 격자가 그보다 크면 축을 균등 간격으로 솎는다
(`shrinkAxes` — 각 축의 **양 끝은 보존**, 최소 2점 유지).

즉 **하드웨어 상수가 리포에 박혀 있지 않다.** 느린 머신에서는 표본이 줄고, 빠른 머신에서는
늘어난다. 어느 쪽이든 10분에 끝난다.

## 3. 새 콘텐츠가 들어올 때 고칠 것

| 새로 들어오는 것 | 하네스 수정량 | 근거 |
|---|---|---|
| **행성** | **0** | `PLANETS` 레지스트리에서 축을 뽑는다 |
| **기체** | **0** | `SHIP_TYPES` 동상 |
| **장비 · 어픽스 · 유니크** | **0** | 표준 세트가 정본 `rollItem` 을 그대로 굴린다 |
| **스킬 노드** | **0** | 표준 투자가 `flattenShipNodes` 에서 파생된다 |
| **만렙 상향 · 밴드 재정의** | **0** | `BAND_LEVELS` 가 `LEVEL_CAP` / `LEVEL_PER_STAGE` 에서 파생된다 |
| **런 입력(촉매·의뢰 등)** | **0** | `buildRunConfig` 단일 정본을 거치므로 기본값이 자동 반영. 그 축을 **변인으로 쪼갤 때만** `axes.ts` 에 축을 하나 추가 |
| **새 지표** | **1줄** | `metrics.ts` 의 `RUN_METRICS` 에 한 줄. 집계·표·게이트가 전부 이 객체를 순회한다 |
| **새 게이트** | **0줄**(위와 동시) | 지표에 `target` 을 적으면 게이트가 자동 생성된다 |

`tests/balanceHarness.test.ts` 가 이 계약을 지킨다 — 누군가 축을 하드코딩 목록으로 되돌리면
테스트가 깨진다. (이 리포가 반복해서 겪은 결함이 정확히 "카탈로그는 늘었는데 목록이 안 늘어
조용히 빠짐"이다.)

**축이 늘어난 대가는 시간이 아니라 표본 정밀도다.** 행성이 6→8 이 되면 소요는 그대로고 셀당
시드 수가 줄어든다.

## 4. 게이트

`src/bench/balance/metrics.ts` 의 `target` 이 정본이다. 2026-08-01 현재:

| 지표 | 밴드 | 범위 | 근거 |
|---|---|---|---|
| 클리어율 | 60~80% | **레벨별** | ADR-0037 표준 빌드 합격선 |
| 클리어초 | 60~190s | 전체 | `RUN_SECONDS_PAR = 95` 의 0.63~2.0배 |
| 타임아웃 | 0~2% | **레벨별** | 구조 건전성(18,000틱 상한에 걸리는 런은 사실상 없어야 한다) |
| 런내 레벨업 | 5~8 | 전체 | ADR-0036 개정 2 |
| 장비유입 | 2~3 | 전체 | ADR-0035 §3.1 |

표본이 0 인 지점은 **위반이 아니라 미판정**으로 센다(승리 0건인 셀의 클리어초를 위반으로
세면 "너무 빠르다"는 거짓 신호가 된다).

### ⚠️ `scope` 를 고르는 법 — 전체 평균은 국소 이상을 가린다

`scope` 는 `'overall'`(기본) 또는 축 이름(`'level'`·`'planet'`·`'ship'`)이다. 축을 주면 **그
축으로 접은 점마다** 판정하고, 위반 지점이 리포트에 이름으로 찍힌다.

`timeoutRate` 가 이 선택이 왜 중요한지 보여준다. `'overall'` 이던 동안 전체 0.8% 로 **게이트가
초록이었는데**, 레벨별로 보니 **Lv100 만 10.6%**(그중 니플헤임 44.8%)였다 — 만렙 추격 런의
절반 가까이가 5분을 넘겨도 끝나지 않고 있었다.

**새 지표에 `target` 을 달 때 먼저 답해라: 이 성질이 전체 평균으로 성립하면 충분한가, 아니면
구간마다 성립해야 하는가.** 구조 건전성·난이도 곡선처럼 "어디서나 참이어야" 하는 축은 반드시
축 단위로 본다.

### 게이트가 없는 진단 지표 (판정은 안 하되 처방을 가른다)

| 지표 | 무엇을 가르는가 |
|---|---|
| `보스도달초`(`bossReachSec`) | **무대 페이싱의 정본.** 목표는 90초(2026-08-01 지시). `클리어초` 는 보스전 소요를 포함해 이 목표를 직접 재지 못한다 |
| `장치잔존`(`chaseDevicesLeft`) | 추격 타임아웃이 "장치를 못 깬 것"인지 "취약화 후 못 잡은 것"인지 |
| `미수거전리품`(`lootGround`) | 장비유입 부족이 **드랍이 적은 것**인지 **줍지 못하는 것**인지 |
| `맵상실`(`mapLossRate`) | 패배가 **플레이어 사망이 아닌** 비율(오염 임계 · 무적 포식자 접촉 즉사). 크면 처방이 확산 시계·포식자 접근 쪽이다 |
| `정화율`(`purifyEnd`) | 오염 무대의 목표 진척. 패배 런에서 낮게 고이면 사인은 압박이 아니라 **목표 총 HP** 다 |
| `지형피해분`·`접촉피해분` | 잃은 HP 의 귀속. 잔차(1 − 둘)는 원거리 탄 + 직접 피해(압사·압박) |

⚠️ `보스도달초` 는 **승리 런만** 본다(`winPosMean`). 승률이 낮은 무대에서는 "빨리 깬 런"만
표본에 남아 값이 **아래로 편향**된다 — 톡사르에서 같은 설정이 3분 단일 행성 런 63.8초 · 8분
전체 격자 94.2초로 갈렸다. **승률이 낮은 무대의 페이싱 수치는 승률을 고친 뒤 다시 재라.**

### 레버가 연결돼 있는지 먼저 확인해라

이 리포는 "**레버를 4배로 돌렸는데 결과가 10% 움직이는**" 상황을 두 번 겪었고, 두 번 다 원인이
밸런스가 아니라 **그 오브젝트가 자동 조준 대상이 아니었다**는 것이었다(추격 반격 장치 · 오염
노드). 수치를 더 올리기 전에 **입력 대비 출력의 크기**를 먼저 보라 — 비례하지 않으면 그 축은
연결돼 있지 않은 것이고, 계속 올리면 없는 문제를 튜닝하게 된다. 목표 오브젝트 판정 정본은
`src/sim/modes/objective.ts` 다.

### 집계 규칙만 바꿔 다시 해석하기 (재측정 없음)

```bash
node scripts/balance/run.mjs --no-build --reanalyze=.balance/final
```

`runs.json` 을 다시 읽어 리포트·요약만 재생성한다. 시뮬레이션을 한 번도 돌리지 않으므로
몇 초면 끝난다. 위 `timeoutRate` scope 수정이 실제로 이 경로로 검증됐다 — 지표 정의나 게이트
밴드를 손봤을 때 10분을 다시 쓸 필요가 없다.

## 5. 사용법

```bash
pnpm balance
```

```bash
pnpm balance:quick
```

주요 인자(`pnpm balance -- --인자` 형태로 준다):

| 인자 | 뜻 |
|---|---|
| `--minutes=N` / `--seconds=N` | 예산(기본 10분) |
| `--workers=N` | 워커 수(기본 코어−2) |
| `--planets=0,3` `--ships=0` `--levels=5,50,100` | 축 부분 선택 |
| `--min-rounds=N` | 격자 축소 시 지키려는 셀당 시드 수(기본 8) |
| `--max-rounds=N` | 셀당 시드 상한(기본 96) |
| `--out=DIR` | 산출 폴더(기본 `.balance`) |
| `--gate` | 게이트 실패 시 exit 1 (CI용) |
| `--no-build` | 직전 번들 재사용 |
| `--verbose` | 라운드마다 로그(기본은 5초에 한 줄) |
| `--reanalyze=DIR` | `DIR/runs.json` 을 다시 집계해 리포트만 재생성(시뮬 미실행) |

### 산출물 (`.balance/`, gitignore 대상)

| 파일 | 내용 |
|---|---|
| `report.md` | 사람이 읽는 리포트(판정 · 곡선 · 편차 · 극단 셀 · 자인) |
| `summary.json` | 게이트 · 셀 통계 · 축 접기 · 편차 요약 |

남길 값이 있으면 `report.md` 를 `.omc/research/` 로 복사한다 — 거기가 계측 정본 자리다.

## 5.1 지표를 모드 사이에서 읽을 때 (⚠️)

**모드마다 같은 이름의 사건이 다른 것을 가리킨다.** 지표를 무대 간에 나란히 놓을 때 같은 것을
세고 있다고 가정하지 마라.

`보스교전`(`bossReachRate`)이 그 예다. 정의는 "**교전 가능한** 보스 엔티티를 본 적이 있는가"이고
모드별 실체는 이렇다:

| 모드 | 보스에 이르는 경로 |
|---|---|
| 뱀서류 · 수축 · 오염 · 레이싱 · 블록격파 | 웨이브를 다 헤쳐 보스 세그먼트 진입 → 보스 스폰 |
| **추격**(니플헤임) | 포식자가 **런 시작부터 존재**하되 무적. 반격 장치 5개를 다 깨야 취약화(`aux0=1`)되고 그때부터 교전 가능 |

처음 구현은 이 지표를 `state.wave.boss`(웨이브 디렉터가 보스 세그먼트인가)로 정의했는데,
추격 모드는 **승리조차 그 세그먼트에 닿기 전에 성립한다**(승리 = 취약화된 포식자 처치, 세그먼트
전진은 대피소 도달로 별개). 결과는 니플헤임 2,240런 중 **승리 422건이 전부 `보스교전=0`** 이었다 —
게이트는 통과하는데 지표가 아무것도 보지 않는 상태였다.

판정은 `src/bench/balance/cell.ts` 의 `bossEngageable` 하나에 모여 있고,
`tests/balanceHarness.test.ts` 의 **"승리 런은 보스를 관측한다"** 불변식이 이 부류의 재발을
막는다(PvE 승리는 곧 보스 처치이므로 구조적으로 참이어야 한다).

**새 모드를 추가할 때**: 그 모드의 승리·진행 경로가 기존 지표 정의와 어긋나는지 먼저 확인하고,
어긋나면 `bossEngageable` 처럼 **판정을 한 곳에 모아** 모드 분기를 넣어라.

## 6. 이 측정이 덮지 못하는 것 (자인)

- **액티브 스킬은 발동되지 않는다.** `autopilotInput` 이 `special` 로 파워업 선택만 낸다
  (`src/sim/autopilot.ts`). 액티브 축(ADR-0041)은 이 격자에 들어오지 않는다. 봇에 발동이
  들어오면 `src/bench/balance/cell.ts` 에 표준 액티브 세트 한 줄만 추가하면 된다.
- **봇은 최적 플레이가 아니다.** 카이팅 + 탄 회피 휴리스틱이라(ADR-0008) 절대 클리어율은
  사람보다 낮다. 이 리포트가 판정하는 것은 절대값이 아니라 **축 간 상대 난이도와 밴드 이탈**이다.
- **파워업 선택은 항상 0번**이다. 파워업 조합의 강약은 이 측정으로 갈리지 않는다.
- **표준 장비는 시드당 한 벌이 아니라 `(기체, 시드)` 당 한 벌이다**(2026-08-02 수정,
  `cell.ts` `gearSeed`). 예전에는 `standardEquipped` 가 기체를 안 받아 한 시드 안에서 기체
  7종이 **같은 장비**로 돌았고, 그래서 `(행성, 레벨)` 한 점의 유효 표본이 √7 배 부풀려져
  **장비 운이 레벨 곡선의 굴곡으로 위장**했다. 대신 기체 비교의 짝짓기(장비 통제)를 잃는다 —
  로스터 편차는 기체당 수백 런으로 접어 그 운이 평균되므로 그쪽이 손해가 작다.
- **침공(PvP)·의뢰 런은 이 격자에 없다.** 각각 `tests/invasionBalance.test.ts` 와 의뢰 계측이
  별도 축이다.

## 7. `rosterBench` 와의 관계
